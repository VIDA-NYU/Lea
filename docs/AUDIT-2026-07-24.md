> **Scope:** the whole `lea-ecosystem` monorepo — the FastAPI adapter, the vendored
> prover, the Overleaf companion + extension, and the React UI — reviewed against
> `issue_address` @ `674e76b` (plus the uncommitted per-run-model change in the
> working tree).
>
> **Method:** source read of every adapter module, the prover's tool/sandbox layer,
> the companion's server seam, and the UI's rendering path; claims verified against
> the code and, where cheap, executed (regex and path-join behaviour were run
> directly). **Analysis only — no source files were changed.**
>
> **Baseline:** all suites are green at the time of writing — 462 adapter pytest
> tests, the Overleaf companion suite, and the UI frontend suite. Every finding
> below is therefore something the existing tests do **not** cover.
>
> **Relationship to prior work:** `apps/overleaf-extension/AUDIT.md` (2026-07-06)
> and [SYSTEM-REVIEW-2026-07-10.md](SYSTEM-REVIEW-2026-07-10.md) covered the
> companion and the design-level shape of the Overleaf path. Their load-bearing
> fixes still hold (atomic serialized JSON writes, the companion's origin
> allowlist, the ledger status engine). This audit therefore centres on the
> **adapter and the prover seam**, which have grown a lot since and have had less
> adversarial attention.

## What is genuinely solid

Worth stating, because it sets the bar the findings are measured against:

- **The concurrency primitives are well-reasoned.** `db.write()` (BEGIN IMMEDIATE),
  the `timeline.id`-as-ordering-key merge, and `runregistry.try_admit` (check-is-the-claim)
  are correct, and their docstrings explain the failure modes they replaced with
  measured numbers. This is unusually good.
- **The "SQL owns proof content" inversion is consistently enforced.** There is no
  surviving code path that stores a git pointer as proof content.
- **Migrations + pre-migration snapshots** (`migrations.py` / `backup.py`) are real,
  and the "snapshot fails → migration doesn't run" policy is the right call.
- **The companion's origin hygiene is exemplary** — it not only sets a narrow CORS
  allowlist but *rejects* requests carrying an unrecognized browser `Origin`
  (`server.mjs:3119-3128`), because a cross-site simple request still executes
  server-side. That reasoning is correct, and the adapter does not have it (S1).
- **No XSS in either UI.** KaTeX runs with `trust: false`, the React markdown path
  segments before rendering, and every `innerHTML` in `content.js` is a static
  template with dynamic values assigned via `textContent`.

## Security

<a id="s1"></a>
### S1 — The adapter has no authentication and no `Origin`/`Host` validation (High)

**Where:** `adapter/app/main.py:20-26`, `adapter/app/routes/sessions.py:336-362`,
`adapter/run_api.py:12-19`

The adapter binds `127.0.0.1:8001` and adds `CORSMiddleware` with a two-entry
allowlist. That is the *entire* access-control story for an API that can start
runs which execute arbitrary shell commands, delete projects, push to GitHub, and
read/write files. Two gaps make the CORS allowlist much thinner than it looks:

1. **The WebSocket endpoint is not covered by CORS at all.** Browsers do not apply
   the same-origin policy to WebSockets, and `lsp_socket` performs no `Origin`
   check. Any page the user visits can open
   `ws://127.0.0.1:8001/api/sessions/<id>/lsp`, which spawns a `lake serve`
   process per connection. Worse, the client controls the document URI and the
   proxy's rewrite is a blind prefix (`lsp_proxy.py:61-75`): a client sending
   `file:///../../../../etc/passwd` becomes
   `file:///<lake_root>/../../../../etc/passwd`, so LSP diagnostics/hover become
   an arbitrary-file read primitive. Session ids are UUIDs, but they leak into
   the Overleaf pane and the UI's URL, and the endpoint 404s in a distinguishable
   way.
2. **CORS does not defend against DNS rebinding.** An attacker domain that
   re-resolves to `127.0.0.1` makes every request same-origin from the browser's
   point of view, so no CORS check fires at all. The companion's `Host`-agnostic
   sibling has the same shape but at least rejects unknown `Origin`s outright.

#### ✅ Fixed (2026-07-24)

New `app/netguard.py` plus an `enforce_local_boundary` HTTP middleware in `main.py`
that **rejects** — rather than merely fails to decorate — any request carrying a
non-loopback `Origin` or `Host`. `CORSMiddleware` is kept, but only to add response
headers to calls that already passed; it is no longer load-bearing.

**The rule is loopback identity, not an exact allowlist.** A localhost service is
legitimately addressed as `localhost`, `127.0.0.1`, or `[::1]` on whatever port the
deployment uses, and the ports differ per deployment: the Vite proxy has no
`changeOrigin`, so it forwards `Host: localhost:5173`, while the single-container
build is reached on `:8001`. Matching hostname and ignoring port covers all of them
with nothing to maintain, and gives up nothing — a remote page cannot present a
loopback hostname in `Origin`, and a rebinding attack cannot present one in `Host`,
since substituting its own name is the entire mechanism. `LEA_ALLOWED_ORIGINS` /
`LEA_ALLOWED_HOSTS` extend both sets for a reverse proxy or LAN name.

**The WebSocket checks itself.** HTTP middleware never sees a handshake, so
`lsp_socket` runs the same check before `accept()` and closes with 1008 otherwise.

**The LSP URI rewrite is now confined.** `rewrite_client_to_server` prefixed
`file://` and nothing else, so a client-supplied `file:///../../../../etc/passwd`
resolved to a real file and the Lean server would read it back through diagnostics
and hover. Escaping URIs are now left *unprefixed* — naming nothing the server will
open — rather than being redirected at a real file. A path that uses `..` but
normalizes back inside the root is still allowed: containment after normalization is
the test, not the presence of `..`.

**Not done:** a shared loopback token. The boundary above closes the browser-borne
attack, which is the reachable one; a token would additionally authenticate *local
processes*, which this design has always trusted. Worth revisiting only alongside
[X3](#x3) (the unbounded `lake serve` spawn), which is the remaining
resource-exhaustion path through the same endpoint.

**Tests:** `test_netguard.py` (31) — the unit rule across remote origins, suffix
lookalikes, `null`, and non-http schemes; loopback origins and hosts on every port
shape including `[::1]`; rebinding hostnames; the env escape hatch; then end-to-end
middleware tests asserting a cross-site `GET` **and** a cross-site `POST /api/runs`
are stopped rather than merely unreadable, that the dev proxy and bundled UI still
work, that a no-`Origin` client (the Node companion) is unaffected, and that the LSP
socket refuses a remote origin. `test_lsp_proxy.py` (+3) — traversal refused,
normalize-back-inside allowed, ordinary rewrite unchanged.

**Verified against the pre-fix code:** 7 of these fail with the middleware, the
WebSocket check, and the URI confinement removed.

### S2 — `_GITHUB_REMOTE_RE` doesn't pin the host: push exfiltrates the GitHub PAT (High)

**Where:** `adapter/app/routes/projects.py:90`, `:339-366`; `adapter/app/gitstore.py:45-58`

```python
_GITHUB_REMOTE_RE = re.compile(r"^https://[\w.\-]+/[\w.\-]+/[\w.\-]+$")
```

The error message says *"Enter an https GitHub repo URL"*, but the pattern accepts
**any** host. Verified: `https://evil.example.com/a/b` matches. `_push_project`
then calls `push_to_github(repo, remote_url, token)`, and `_inject_token` embeds
the credential in the URL:

```
https://x-access-token:<PAT>@evil.example.com/a/b
```

git sends that in the `Authorization` header of the initial `GET /info/refs`
request, so the attacker's server receives the user's GitHub Personal Access
Token before any push is even attempted. The whole project's contents follow.

There is no auth on `PUT /api/projects/{id}/git/remote` either, so this is
reachable by anything that can reach the API (see S1), not just by a user who
mistypes a URL.

#### ✅ Fixed (2026-07-24)

Defended at two layers, because input validation alone leaves the stored row as an
unguarded second entry point.

**1. The credential boundary** — `gitstore._inject_token` (`gitstore.py:45-77`) now
refuses to embed the token unless the URL is `https` *and* its host is in the new
`GITHUB_CREDENTIAL_HOSTS` allowlist (`github.com`, `www.github.com`,
`gist.github.com` — the last is required by `ghimport`'s private-gist clone path).
Anything else comes back untouched, so the push proceeds unauthenticated and fails
rather than authenticating to a stranger. `http` is now excluded as well: the
credential must not travel in cleartext, and nothing in the codebase builds an
`http` GitHub URL.

This is the layer that actually matters. `_inject_token` is the one place the token
enters a URL, so putting the check there means every present and future caller
inherits it — the previous shape depended on whichever route happened to build the
URL having validated it.

**2. Route input validation** — `_GITHUB_REMOTE_RE`
(`routes/projects.py:90-108`) is pinned to `^https://(?:www\.)?github\.com/…$`, and
each path segment must start with a word character or hyphen so `..` can't appear
as an owner or repo. `_push_project` (`routes/projects.py:373-386`) re-checks the
stored value at the moment the credential would be used, because a row written
before the pin — or by anything that touches `projects.remote_url` directly — must
not become a delivery target either. Non-http(s) remotes (local paths, ssh) skip
that check, since they can't carry the token; that keeps the existing
push-to-local-bare-repo tests meaningful.

**Tests:** `test_gitstore.py` — `_inject_token` embeds for github.com/gist, and a
parametrized case asserts the token appears *nowhere* in the result for the
exfiltration target, a `github.com.evil.example.com` suffix-lookalike,
`raw.githubusercontent.com`, cleartext `http`, and an ssh remote; plus an
end-to-end push to a dead non-GitHub https host asserting the token is absent from
the error. `test_routes_projects.py` — the route rejects five hostile URL shapes
and leaves `remote_url` unset, still accepts both legitimate shapes, and a
directly-stored legacy remote is refused at push with `push_to_github`
monkeypatched to fail loudly if it is reached at all.

**Note for reviewers:** the suffix-lookalike case (`github.com.evil.example.com`)
is why this is a host-equality check on `urlparse().hostname` rather than a
`startswith`/`in` test on the URL string.

### S3 — Path traversal in the standalone check/rebuild/verify endpoints (High)

**Where:** `adapter/app/routes/sessions.py:400-416`

```python
rel = path or _latest_proof_path(session_id)
...
return str(repo / rel), rel
```

`rel` comes straight from the request body (`PathRequest.path`) and is joined onto
the repo with **no containment check**. `repo / "../../../../etc/passwd"` resolves
outside the session directory — verified. Three endpoints use it:

- `POST /api/sessions/{id}/lean-check` — runs Lean over the target file and returns
  `detail`, which for a non-Lean file is a parse error that quotes source lines.
- `POST /api/sessions/{id}/rebuild` — runs `lake build` against it.
- `POST /api/sessions/{id}/verify` — runs SafeVerify against it.

`lean-check` with `author` set additionally writes a new `code_step` row for the
traversed path, polluting the timeline.

The correct guard is *three functions away in the same file*:
`write_file_session` does exactly this (`sessions.py:193-197`), and
`filesystem._safe_abs` and `routes/projects._resolve_repo_file` each implement it
again. `_resolve_proof_path` is the one that was missed.

#### ✅ Fixed (2026-07-24)

`filesystem._safe_abs` was **promoted to public `filesystem.safe_abs`**
(`filesystem.py:39-60`) and `_resolve_proof_path` now goes through it
(`routes/sessions.py:400-433`), raising `400` on an escape. That also inherits the
`IGNORED_DIRS` guard, so `.git/config` and the `.lake` build tree are out of reach
too — neither was in the original report, both were reachable.

Promoting the helper rather than inlining a fourth copy is the point of the fix.
The containment logic existed in three places (`write_file_session`,
`filesystem._safe_abs`, `routes/projects._resolve_repo_file`) and the bug was a
*missing* copy, not a wrong one. One shared function means the next path-joining
route can't reintroduce it by omission; the docstring says so explicitly.

`_resolve_proof_path` now also returns the **normalized** relative path
(`abs_path.relative_to(repo.resolve()).as_posix()`), which is the same form
`bridge._relativize` writes into `timeline.path` — so the `latest_code_step_for_path`
lookups keyed on it are unaffected, and an un-normalized spelling
(`./Lea/Other/../Misc/p.lean`) now resolves onto the same code step instead of
silently missing it. That is a small bonus fix.

**Not done — and deliberately:** the report also suggested rejecting non-`.lean`
paths. I left that out. Every current caller passes `.lean`, but the default path
comes from the session's latest code step, and I could not establish from the code
that a non-`.lean` step can never reach these endpoints (the cascade path in
particular is driven by the companion). Containment is the security fix and is
provably behaviour-preserving; an extension filter is a behaviour change that
wants its own reasoning. Worth revisiting.

**Tests:** `test_routes_sessions.py` — a parametrized case drives all three
endpoints with five escape shapes (plain traversal, traversal behind a legitimate
prefix, an absolute path, `.git/config`, `.lake/...`) with `interface_check`,
`interface_verify`, and `interface_rebuild` all monkeypatched to raise if reached,
so the assertion is "the toolchain never ran", not merely "a 400 came back"; plus
a case pinning that the `author=` branch refuses *before* writing its cascade
code_step, and one asserting legitimate in-repo paths still resolve and normalize.

**Verified against the pre-fix code:** with the guard reverted, all 7 new tests
fail. They are pinning the bug, not the implementation.

### S4 — Prompt injection from a mirrored Overleaf document reaches an unsandboxed shell (High)

**Where:** `prover/lea/tools.py:430-447` (`bash`), `:143-156` (`read_file`),
`adapter/app/bridge.py:1049-1051` (`gate=None` when autonomous),
`adapter/app/projects.py:214-234` (mirrored `.tex` folded into the context)

This is a chain, and each link is individually documented as an accepted tradeoff.
Composed, it is the sharpest exposure in the system:

1. The extension mirrors the Overleaf project's `.tex` sources into
   `.lea/files/overleaf/` and `compose_context_message` tells the agent to
   "Consult them for the prose statements, notation, and definitions". The `.tex`
   is attacker-influenced content whenever the Overleaf project has a collaborator,
   is shared from a link, or is a template.
2. Every Overleaf-driven run is **autonomous by construction** (D19): `run_events`
   is called with `gate=None`, so no tool ever pauses for approval.
3. `bash` is `subprocess.run(command, shell=True)` with no allowlist, no jail, and
   only `cwd` set. `cwd` is a starting directory, not a boundary.
4. `read_file` has **no confinement whatsoever** — unlike `write_file`/`edit_file`,
   which go through `_sandboxed_write_path`. So the model can read
   `~/.ssh/id_rsa`, the monorepo `.env`, and `config/lea.local.toml` (every
   provider key and the GitHub PAT, in plaintext).

The `_sandboxed_write_path` guard (`tools.py:162-198`) is thoughtful, but it
protects one tool while `bash` — in the same default toolset — bypasses it
entirely (`bash("cp /tmp/x /anywhere")`). It is worth being explicit in the
design docs that the write sandbox is a *typo/hallucination* guard, not a
security boundary, so nobody later reasons from it as if it were one.

#### ◑ Partly fixed (2026-07-24)

The chain has four links. Three are now cut; the fourth is the standing trust
assumption and is called out as such rather than quietly narrowed.

**1. `read_file` is confined** (`prover/lea/tools.py`). Reads are limited to the
run's `working_dir` **and its enclosing Lake root**. Both roots are required, and the
second is the whole subtlety: confining to the workspace alone would have broken the
normal proving loop, because `search_mathlib` hands back paths under
`.lake/packages/mathlib/` and the model reads them on the next turn. With that
boundary, `~/.ssh/id_rsa`, the monorepo `.env`, and `config/lea.local.toml` — which
holds every provider key and the GitHub token in plaintext — are all out of reach,
while sibling sessions in the same project stay readable (the design encourages
cross-session imports).

**2. The shell no longer carries credentials.** Confining reads would have been
half a fix: `load_config` exports every configured provider key into this process for
LiteLLM, which also put them in the environment of every command the model ran, so
`echo $OPENAI_API_KEY` needed no filesystem access at all. `bash` now runs with a
`scrubbed_env()` — anything matching `*_API_KEY`/`*_TOKEN`/`*_SECRET`/`*_PASSWORD`/
`*_CREDENTIALS` plus a few named exceptions is withheld. Nothing legitimate needs
them: Lean, Lake, and git don't, and the adapter injects the GitHub token into its
own push URL rather than through the environment.

**3. The mirrored `.tex` is framed as data.** `compose_context_message` now states
that the Overleaf sources are untrusted data rather than instructions, and that text
appearing to address the agent directly — asking it to run a command, read or send a
file, or ignore its instructions — is not a request from the user and should be
reported rather than obeyed. Cheap, no behaviour change, and it targets the specific
reason this path is exposed: an Overleaf project can have collaborators, be shared by
link, or come from a template.

**4. NOT fixed — `bash` still runs arbitrary commands.** Autonomous runs still reach
an unrestricted shell. I did not gate it, and the reason is that both available
shapes are worse than the disease: an allowlist of `lake`/`git`-shaped commands
would break real usage that I cannot enumerate from the code, and adding an approval
gate would contradict D19, whose entire purpose is a zero-interaction Overleaf path.
The honest fix is the container-per-run that `lsp_proxy.py`'s D63 note already
anticipates, and that is a project, not a patch.

What the three changes do buy is that the *reachable prize* is gone. A prompt
injection can still run commands, but it can no longer read the credentials that
would let it do damage beyond this machine — which was the sharp edge.

**Tests:** a new `prover/tests/tools/test_read_sandbox.py` (21 checks, matching the

### S6 — Secret files are written non-atomically, at default permissions, with no value escaping (Medium)

**Where:** `adapter/app/settings.py:503-559`, `adapter/app/subagent_overrides.py:68`,
`scripts/env.mjs:84`

Three problems in the same write path:

1. **Not atomic.** `path.write_text(...)` truncates first. A crash or a full disk
   between truncate and write leaves `config/lea.local.toml` empty — i.e. every
   provider key and the GitHub token gone. The companion learned this lesson and
   uses temp+rename (`atomicWriteJson`); the adapter did not.
2. **Default permissions.** Neither `lea.local.toml` nor `.env` is chmod'ed; with a
   typical umask they land at `0644`, world-readable on a shared machine.
3. **No value escaping beyond `\` and `"`.** `_toml_scalar` escapes those two
   characters only. A key value containing a literal newline (paste accident,
   or any client hitting `PUT /api/settings` directly — only the three
   first-class providers get format validation, everything matching
   `*_API_KEY` is stored verbatim) produces a basic TOML string spanning two
   lines. `tomllib.loads` then raises on **every** subsequent request, because
   `load_config`, `permission_tier`, `github_token`, and
   `configured_provider_keys` all re-parse the file on every call with no
   try/except. The adapter 500s on essentially every endpoint until the file is
   hand-repaired.

#### ✅ Fixed (2026-07-24)

All three, plus one the fix uncovered.

**Atomic and owner-only.** New `config.write_private_text` writes a temp file in the
same directory (rename is only atomic within a filesystem), `fchmod`s it to `0600`
*before* any content reaches it, `fsync`s, then `os.replace`s. A reader sees the whole
old file or the whole new one, never a stump — and `os.replace` carries `0600` onto
the final path, which also repairs a file that predates this. Used by both
`settings._write_toml_updates` and `subagent_overrides.save_override`, and mirrored in
`scripts/env.mjs` (`writePrivateFile`) for `.env`, which holds the same keys.

**Escaping.** `_toml_scalar` escaped `\` and `"` only. TOML basic strings cannot
carry a raw control character and a literal newline ends the string, so such a value
produced a file `tomllib` then refused to parse — and since only the three
first-class providers are format-validated, anything matching `*_API_KEY` reached the
writer verbatim. Now the standard escapes plus `\uXXXX` for other control characters.

**Tolerant readers.** All four config readers go through `config.read_config_data`,
which degrades to `{}` with a loud log. An unparseable file used to 500 essentially
every endpoint — including the Settings page needed to repair it.

**Found by the fix:** with escaping in place, a NUL byte now *persists* cleanly and
then explodes at `load_config`, which exports every saved key into `os.environ` —
`ValueError: embedded null byte` on the next request. So a NUL is refused at the input
boundary instead. Escaping and rejecting are not alternatives here: escaping protects
the file format, and the rejection protects the environment export, which is a
different constraint. A credential containing a NUL is a mangled paste, not a
credential.

**Tests:** a save leaves the file `0600` with no temp beside it, and repairs an
existing `0644`; a failed `os.replace` leaves the previous settings byte-intact; four
control-character shapes round-trip exactly and keep the file parseable; a NUL is
refused with a field-tagged error and nothing is written; and a deliberately corrupt
file still yields working defaults from `load_config`, `permission_tier`,
`github_token`, `configured_provider_keys`, and `settings_payload`.

**Verified against the pre-fix code:** 5 of the 9 fail.

### C1 — Global usage totals, and therefore the spend cap, only count 100 sessions (High)

**Where:** `adapter/app/store.py:218` (`limit 100`), `:1702-1759` (`usage_stats`),
`adapter/app/settings.py:305-312`, `adapter/app/bridge.py:957-975`

`_list_sessions` ends with a hard-coded `limit 100`. `usage_stats()` computes its
`global` block by summing the Python list `list_sessions()` returns — so
`global.cost_usd` is the cost of the **100 most-recently-updated sessions**, not
of all of them.

Three things consume that number:

- `settings.spend_limit_reached()` → the `402` guard on `POST /api/runs`;
- `bridge.check_spend_cap()` → the mid-run cap that stops a run at a turn boundary;
- the Settings page's `current_spend_usd` and the whole Stats page.

Once a user passes 100 sessions, the reported spend **decreases** as old sessions
fall out of the window, so a configured `max_spend_usd` silently stops being
enforced — exactly the failure mode the cap exists to prevent. The `daily` and
`models` rollups in the same function are computed with proper SQL aggregates over
the full table, so the Stats page will show a `global` total that disagrees with
its own daily chart.

#### ✅ Fixed (2026-07-24)

Two new full-table aggregates in `store.py` (`store.py:1702-1760`):

- **`global_usage()`** — one query counting every session, every non-code timeline
  row, and every run's tokens/cost. `usage_stats()["global"]` is now just this.
- **`total_spend_usd()`** — a single `SELECT coalesce(sum(cost_usd), 0) FROM runs`.
  Kept separate from `usage_stats()` deliberately: the cap is checked at every turn
  boundary and on every `UsageUpdated` event, and routing that through the full
  stats payload is both what made it wrong *and* a heavy per-event query.

Both spend-cap readers now use the scalar — `settings.current_spend_usd`
(`settings.py:305-310`, which `spend_limit_reached` and so the `402` on
`POST /api/runs` sit on) and `bridge.check_spend_cap` (`bridge.py:957-975`).
`settings_payload` no longer builds the whole stats payload just to read one number.

**`_origin_rollup` was fixed too**, and it wasn't in the original write-up. It folded
the same truncated page, and its docstring promised *"aggregated from the same
`sessions` rows the `global` totals come from, so the two always agree"* — which
was true, and was the problem: they agreed while both were wrong. It is now a
`GROUP BY origin` aggregate over the full `sessions`⋈`runs` join, so the promise
holds for the right reason (`store.py:1774-1820`).

`usage_stats()["sessions"]` is **still** the 100-row page — truncating a rendered
table is fine, and a comment now says so. The rule the fix encodes: *a total over
"everything" is a SQL aggregate over everything; a paginated list is for rendering,
never for arithmetic.*

**Tests:** `test_store.py` — 120 sessions and the global block reports all 120
while `stats["sessions"]` still returns 100, plus an assertion that `global` now
agrees with the `daily` and `models` rollups beside it (those were already correct
full-table aggregates, so the Stats page was disagreeing with its own chart);
`total_spend_usd` over 150 sessions; the end-to-end cap consequence (150 sessions
at $0.50 against a $70 and a $100 cap — the old path saw the newest 100 and
reported "under the limit"); and an origin rollup over 120 sessions that must sum
to `global`.

**Verified against the pre-fix code:** with `global`/`origins`/`total_spend_usd`
restored to the page-folding shape, all 4 fail.

**Note:** this removes the *heaviest* part of [P2](#p2) — `check_spend_cap` no
longer runs `_list_sessions`' six correlated subqueries per usage event — but P2
stays open: a `SELECT sum()` per event is cheaper, not free, and the memoization
that finishes the job hasn't been added. [C4](#c4) (the same `limit 100` truncating
*search*) is also still open; it needs `_list_sessions` to take a caller-supplied
limit, which this fix deliberately didn't touch.

### C2 — `_project_has_active_runs` cannot detect a run in a session that already has code (High)

**Where:** `adapter/app/projects.py:487-488`, `adapter/app/store.py:1665-1691`

```python
def _project_has_active_runs(project_id: str) -> bool:
    return any(session.get("status") == "running" for session in store.list_project_sessions(project_id))
```

But `_derive_session_status` returns `"running"` **only when the session has no
code steps yet**:

```python
if code_step_count:
    ... return the verdict          # "proved" / "ok" / "error" / ...
if has_active_run:
    return "running"
```

That is deliberate (D14: status is a working-copy verdict, not run lifecycle) —
the guard just read the wrong field. Any project session that has ever written a
file reports `proved`/`ok`/`error` while a run is live.

The consequence is severe: `migrate_project_namespace` uses this as its only
safety interlock, then rewrites every `.lean`/`.md` in the repo and
`shutil.move`s the whole directory. Renaming a project's namespace while an agent
is mid-run moves the working tree out from under it — the run's `write_file` calls
recreate the old path, the code steps point at a directory that no longer exists,
and the migration's own `lake` re-check races the agent's writes.

The correct signal is right there on the same row: `_list_sessions` already
computes `active_run_count` (`store.py:193-196, 230, 238`).

#### ✅ Fixed (2026-07-24)

New `store.project_has_active_run(project_id)` (`store.py:1402-1424`) — a direct
`SELECT 1 FROM runs JOIN sessions … WHERE status IN ('pending','running') LIMIT 1`
— and `projects._project_has_active_runs` (`projects.py:487-496`) now delegates to
it.

Taking the query rather than the `active_run_count` column was the deliberate
choice: the column is only available on the `_list_sessions` aggregate, so using it
would have meant running that 100-row six-subquery aggregate to answer a boolean —
and it inherits the same `limit 100` truncation as [C1](#c1), so a project's
101st-oldest session would have been invisible to the interlock. A safety check
should not be able to miss things because a list was paginated.

The join goes through **`sessions.project_id`, not `runs.project_id`**, and the
docstring says why: `repo_for_session` picks the on-disk repo from the session's
project tag, so that is the link that decides whose working tree a run is writing
to — which is exactly what this interlock protects.

**Tests:** `test_projects.py` — the load-bearing case is a project session that has
a code step *and* a running run, asserting both that its derived status is `"ok"`
(not `"running"` — pinning the D14 behaviour the old predicate misread) and that
the interlock fires anyway; the pre-code case the old check *did* catch, so the fix
can't regress it; the terminal-run case; the end-to-end migration refusal
(`project_busy`/409, with assertions that the repo did **not** move and the index
still names the old namespace); and an idle-project rename that must still succeed,
so the guard doesn't become a blanket refusal.

**Verified against the pre-fix code:** with the predicate restored, the
established-session detection and the migration refusal both fail — the migration
runs to completion and moves the repo.

**Still open, related:** the check is a TOCTOU — a run can be admitted between the
interlock and the `shutil.move`. Narrowing that needs the same
atomic-`UPDATE`-and-branch treatment as [C7](#c7), and is out of scope here.

### C3 — `_promote_winner` overwrites the canonical proof before re-verifying it (High)

**Where:** `adapter/app/bridge.py:837-855`, `adapter/app/collation.py:139-160`

```python
collation.promote(winner, canonical)          # writes the file
verdict = _lean_check_file(str(canonical))    # then checks it
if verdict.status != "ok":
    logger.warning(...)
    return None                               # ...and leaves the bad file in place
```

The re-verification guard is the right idea — the docstring even explains why the
child's own verdict can't be trusted at a new path. But the check happens *after*
the write, and the failure path doesn't roll back. Two ways that loses work:

1. If a proof already existed at `<namespace>/<candidate-name>.lean` (a previous
   run's verified output), it is destroyed on disk and replaced by a candidate
   that just failed to compile. The DB still holds the old bytes, but the
   filesystem is what Lean compiles, what `/export` zips, and what `git push`
   ships — and the code_step is never written, so nothing records that the file
   changed.
2. The canonical path is derived from the **child's scratch filename**
   (`Path(winner.candidate_path).name`), so two unrelated children with the same
   scratch name collide onto the same canonical path.

#### ✅ Fixed (2026-07-24)

`_promote_winner` snapshots whatever stands at the canonical path before
`collation.promote` overwrites it, and restores it when the re-verification fails
(`bridge.py:926-1035`).

**Restore-on-failure rather than verify-then-move**, which is what the original
write-up suggested and is wrong here. Lake resolves modules by location, so the path
is part of what is being verified — checking at a temp path would verify something
other than what we are about to keep, and would quietly weaken the guarantee the
re-check exists to provide. The comment in the code says so, because the temp-path
version is the obvious "improvement" someone will reach for later.

`_snapshot_file` distinguishes three states, and the distinction is the fix: bytes,
`_ABSENT` (nothing was there — restore by deleting), and `None` (a file was there but
could not be read). On `None` the file is **left as promoted**: there is nothing to
put back, and deleting would convert a bad overwrite into outright data loss.

**Correction to the original finding.** It also claimed two children with the same
scratch filename could collide onto one canonical path. That is wrong — only the
single winner is ever promoted, so there is no intra-run collision. The real residual
risk is narrower: a *successful* promotion still replaces a same-named file from an
earlier run, which is the same thing the coordinator writing that filename would do,
and it is recorded as a code_step either way.

**Tests:** a failed re-verification leaves the previous verified proof byte-identical
on disk and writes no code_step; with nothing there beforehand it leaves no file
behind either; a successful promotion still overwrites and records the step and emits
`promoted`; and an unreadable previous file is left alone rather than deleted.

**Verified against the pre-fix code:** the two restore tests fail — the previous
proof is replaced by the broken candidate, exactly as reported.

### C4 — Search can only reach the 100 most-recently-updated sessions (Medium)

**Where:** `adapter/app/store.py:114-127`

`search_sessions` delegates to `_list_sessions` (capped at 100 rows by the same
`limit 100`) and *then* applies `rows[:limit]`. So the `LIKE` filter runs inside a
query that has already been truncated by recency.

Search is described in `routes/search.py` as *"the only path to a project session:
the sidebar hides in-project sessions (D30), so search is load-bearing, not a
nicety."* It stops finding older project sessions entirely once the workspace
crosses 100 sessions — silently, with an empty result set that looks like "no
match".

#### ❌ Withdrawn (2026-07-24) — this finding was wrong

**Search was never truncated by recency.** The claim above — that the `LIKE` "runs
inside a query that has already been truncated" — misreads the SQL. The `LIKE` *is*
the query's `WHERE` clause, and SQL applies `WHERE` before `LIMIT`, so the cap has
always bounded the number of **matches**, not the window searched. A session matching
the query has always been findable no matter how many newer sessions exist.

Demonstrated directly:

```sql
-- 141 rows, the only match being the OLDEST
select title from s where title like '%needle%' order by updated_at desc limit 100;
-- → [('needle',)]
```

**How it surfaced:** the regression test written for it passed against the *pre-fix*
code. That is the check earning its keep — every fix in this document is verified by
reverting it and confirming the new tests fail, and this is the one case where they
didn't.

**What landed anyway:** `_list_sessions` now takes a caller-supplied `limit` and
`search_sessions` passes its own, so a 30-result search fetches 30 rows instead of 100
and discards 70. A small efficiency change, not a correctness one — and the hard-coded
constant it removes is the same one that *did* cause [C1](#c1), where the mistake was
real because that code summed the page instead of filtering it.

**The lesson worth keeping:** C1 and C4 look like the same bug and are not. Folding a
paginated list in Python truncates the answer; filtering inside the paginated query
does not.

### C5 — Collation's SafeVerify tier is never populated (Medium)

**Where:** `adapter/app/bridge.py:837`, `adapter/app/collation.py:163-185`

The coordinator never does it:

So `_TIER_SV_REJECTED` is unreachable, and a candidate that compiles but cheats

raises is likewise "not run", not "rejected" — otherwise an unbuilt binary would

**Tests:** a rejected candidate is not promoted *and* the good proof it would have
replaced survives; `unavailable` and `error` both still promote; a crashing audit
still promotes; and promotion falls through from a rejected winner to the honest

### C6 — A post-completion bookkeeping error rewrites a successful run to `failed` (Medium)

**Where:** `adapter/app/bridge.py:1327-1351`

The `Finished` branch does, in order: `store.update_run(run_id, final_status, ...)`,
`replace_run_usage_breakdown`, `set_run_transcript`, `_record_run_artifacts`. Those
last three are outside any inner try. If any of them raises — a locked DB, a JSON
serialization failure on the transcript, a disk error — control lands in the outer
handler:

```python
except Exception as exc:
    ...
    store.update_run(run_id, "failed")
    final_status = "failed"
```

which overwrites the terminal status that was just correctly persisted, and emits
`done: {status: "failed"}`. A run that proved the theorem is reported as failed,
and the proof's code steps are stranded under a failed run (which changes the
derived session status via `latest_code_run_status`).

`_record_run_artifacts` is already individually guarded (`bridge.py:515-516`),
which shows the pattern was understood — it just wasn't applied to its neighbours.

#### ✅ Fixed (2026-07-24)

Both halves, as the finding suggested.

**Each bookkeeping step is guarded on its own** via a new `_best_effort` helper, so
one failure neither loses the others nor escapes. They are three separate records of
one finished run, not a transaction — the usage breakdown failing is no reason to
lose the transcript.

**A terminal run is never downgraded.** The outer handler now checks
`_run_is_terminal(run_id)` first: the Finished handler persists the outcome *before*
doing anything else, so a failure after that point is a bookkeeping problem, not a
failed proof. `final_status` is left alone too, so the `done` frame tells the client
the same truth the row holds — previously the run was rewritten to `failed` *and* the
client was told `failed`, for a proof that had succeeded.

A read failure in `_run_is_terminal` answers `False`, falling back to the old
mark-it-failed behaviour: if the database is unreachable we would rather over-report
failure than leave a run looking live.

**What made this worse than it sounds:** the derived session status reads the latest
code step's *run* status (`_derive_session_status`'s `latest_code_run_status`), so
rewriting the run to `failed` also made the whole session read as broken — a proof
that existed, compiled, and was recorded, presented as a failure.

**Tests:** parametrized over the two DB-writing steps, a `sqlite3.OperationalError`
mid-bookkeeping leaves the run `proved`, the session `proved`, and the `done` frame
`proved`; a failure *before* Finished still marks the run failed (the guard must not
swallow real failures); and one failing step does not prevent a later one from
landing.

**Verified against the pre-fix code:** all four fail — the run comes back `failed`.

### C7 — `interrupt_run` TOCTOU against the dispatcher (Medium)

**Where:** `adapter/app/routes/runs.py:212-231`, `adapter/app/bridge.py:136-178`

```python
if run["status"] == "pending" and not runregistry.registry.is_active(run_id):
    store.update_run(run_id, "failed", ...)
```

The dispatcher independently reads `store.get_run(run_id)`, sees `pending`, calls
`try_admit`, and spawns `run_lea`, which sets `status = "running"`. Interleave the
two and you get: endpoint reads `pending` → dispatcher admits and spawns →
endpoint's `is_active` check happens to run before the registry insert lands, or
the endpoint's `update_run("failed")` lands after `run_lea`'s `update_run("running")`.

Both orderings are wrong in a visible way: either the run is reported "interrupted"
and then keeps executing (and billing), or it is marked `failed` while running and
then flips back to `running`, defeating the recovery invariant that a `failed` row
is terminal.

The cooperative `request_stop` flag is set first, so the run *will* stop at its
next turn boundary — but "next turn boundary" on a fresh run can be a full model
call away, and the endpoint has already told the client it's over.

#### ✅ Fixed (2026-07-24)

Two conditional UPDATEs, one from each side of the race:
`store.fail_pending_run` (the endpoint) and `store.claim_pending_run` (the driver),
each `… WHERE id = ? AND status = 'pending'` returning `rowcount > 0`. The check and
the claim are now the same operation, so exactly one can win.

The endpoint's `runregistry.is_active` consultation is gone — the row itself is the
authority, and asking a second source was what made this three steps instead of one.

**A deliberate behaviour change:** a run whose slot is claimed but whose driver has
not started is now cancelled *outright* rather than left to the cooperative path. The
old shape returned `interrupting` with the row still pending, on the theory that the
driver owned it — but the driver had not begun, so the run went on to claim the row,
make a model call, and only then notice the stop flag. Now `run_lea` finds the row no
longer pending and declines to start, so an interrupt at that moment costs nothing.
One existing test asserted the old contract and was rewritten to assert the new one.

**Tests:** claim-then-claim, claim-then-fail, and fail-then-claim all have exactly one
winner; eight threads contending produce exactly one; and both endpoint paths
(cancel-before-start, cooperative-once-running) are pinned.

### C10 — Interrupted and superseded runs store no transcript (Medium)

**Where:** `adapter/app/bridge.py:1336`, `adapter/app/store.py:1149-1169`

`set_run_transcript` is called **only** in the `Finished` branch — deliberately,
per the comment ("an errored run stores none"). But the dispatcher's supersede
path (`bridge.py:183-186`) triggers this automatically: sending a second message
to a session that is mid-run calls `request_stop` on the incumbent, which exits via
`reason="interrupted"`.

An interrupted run reaches `Finished` with `reason="interrupted"`, so it *does*
store a transcript — but a run that raises (a provider error, a timeout) does not,
and `latest_transcript_for_session` then silently falls back to the last run that
did. The user's follow-up therefore replays a conversation that omits the turn
they just watched happen, and the agent re-derives work it already did. There is no

#### ◑ Partly fixed (2026-07-24) — the gap is named, not recovered

The second option in the original write-up, and I want to be clear that the first one
was investigated and **rejected on evidence** rather than skipped.

**Why not persist the partial transcript.** The prover appends the assistant's
`tool_call` message *before* the tools run and the `tool_result` messages after
(`agent.py`, phases 1–3 of the turn). A transcript captured at an arbitrary crash
point can therefore end on a `tool_call` with no matching result — a shape every
provider rejects. Replaying it would convert "this session lost a turn" into "this
session can no longer start one." Recovering the content safely means truncating to
the last complete turn boundary, which the prover would have to expose (its
`transcript()` closure is a local of `_run_events_inner`); that is a prover change
with real blast radius, and it is the honest follow-up if this matters.

transcript. Only crashes land mid-turn.

**What landed instead.** New `store.transcript_gap_for_session` names the terminal

`bridge._transcript_gap_context` turns that into a note prepended to the next run's
task: how many attempts are missing, how each ended, and that their files are still on
disk and reflected in the working copy. The silent hole becomes a stated one.

A pending or running run is not a gap — it has not finished — and a crash that a later
successful run already superseded is not one either, since that run's transcript
covers the conversation. Both are pinned by tests, because a note that fires on every
follow-up is noise rather than information.

**Still open:** the UI shows nothing. The agent is told; the user is not.

**Tests:** the gap is detected and described (including the failure detail); a
continuous history produces no note; a crash older than the newest transcript is not a
gap; an active run is not a gap; and end-to-end, the note actually reaches the task

**Verified against the pre-fix code:** the end-to-end test fails (the task is the bare

### C11 — `requirements_for` reads the process environment, contradicting its own contract (Low)

**Where:** `adapter/app/models_catalog.py:76-100`

The docstring says: *"Whether one is actually configured is decided by the caller

`requirements_for` is now a **pure function of the model**

- **Alternatives.** Anthropic accepts `ANTHROPIC_AUTH_TOKEN` and Gemini accepts

- **Providers with no single key.** Vertex, Bedrock, SageMaker, and Ollama get an
  explicit empty tuple — they authenticate through a cloud credential chain or not
  at all, and the convention fallback would have invented a `VERTEX_AI_API_KEY`
  requirement and refused a working model.

**The consistency half.** `required_keys` being environment-independent is only half
the fix; the other half is that satisfaction is now judged the same way everywhere.
New `settings._key_available(env, saved)` counts a key as configured when it is
saved in the config file **or** already present in `os.environ`, and both
`model_requirements` and `_validate_selected_model_has_key` use it

only the file would refuse a model that demonstrably works — an exported key now

falling through to the family heuristic when LiteLLM recognises the provider,
so a deliberate "no key needed" answer isn't overridden by a guess.

**Tests:** `test_settings.py` — the anchor is a parametrized case across four
providers asserting `required_keys` is **identical with and without the key in the

**Verified against the pre-fix code:** with `requirements_for` restored to the

**Knock-on:** the model-picker feature's `validate_configured_model` guard is now

which is fine — they're testing the error plumbing, not the requirement derivation.

### X1 — The single dispatcher head-of-line blocks; `LEA_MAX_CONCURRENT_RUNS=4` doesn't deliver 4 (High)

**Where:** `adapter/app/bridge.py:131-199`

```python
while True:
    run_id = _run_queue.get()
    while True:                       # ← inner loop, this run only
        ...
        admission = registry.try_admit(...)
        if admission.outcome == ADMITTED: ... break
        if admission.outcome == SESSION_BUSY and admission.incumbent_run_id:
            request_stop(admission.incumbent_run_id)
        time.sleep(0.1)               # ← spins here, holding the queue
```

There is exactly one dispatcher thread, and it does not pull the next queue entry
until the current head is admitted. So:

- **`SESSION_BUSY` blocks unrelated sessions.** A follow-up in session A waits for
  A's incumbent to stop cooperatively — which can be a full model call away, or
  never if the incumbent is stuck on an unanswered approval (up to
  `APPROVAL_DECISION_TIMEOUT_SECONDS = 900`). Meanwhile runs queued for sessions
  B, C, D sit behind it with three free slots.
- **`AT_CAPACITY` is fine on its own** (nothing else could start either), but
  combined with the above, the effective concurrency of the system is well below
  its configured capacity in exactly the multi-chat scenario Phase 6 raised the
  default to 4 for.
- **`request_stop` is re-issued at 10 Hz** for the whole wait. It's idempotent, so
  harmless, but it's a symptom: the loop has no state, it just re-decides.

The registry itself is correct and per-run — the bottleneck is entirely the
dispatcher's shape.

#### ✅ Fixed (2026-07-24)

The inner spin loop is gone. `_worker_loop` now keeps a `deferred` list: a run that
can't be admitted is set aside and retried on the next pass while the dispatcher
carries on draining the queue (`bridge.py:131-247`). One dispatch attempt is
`_try_dispatch`, extracted so it returns `_SETTLED` / `_DISPATCHED` / `_DEFER` and
never blocks.

**FIFO is preserved where it means something.** `deferred` keeps the relative order
of the waiting runs and is retried *before* newly arrived ones, so a blocked run does
not lose its place to a later arrival. What's gone is its claim on everyone else's
turn — which was never FIFO, just head-of-line blocking wearing FIFO's clothes.

**Idle stays free.** The queue is polled (100 ms) only while something is deferred;
with nothing waiting the dispatcher blocks on `get()` exactly as before, so this adds
no background wakeups to an idle adapter.

**The supersede is issued once per incumbent**, tracked in a `superseded` map. The
flag is an `Event`, so repeating was harmless — but the old loop re-issued it on
every 100 ms poll for as long as the incumbent took to wind down, which is noise in
any log that captures it.

**Tests:** the load-bearing one holds an incumbent open in session A, queues a
same-session follow-up behind it (which must defer) and then an unrelated session's
run, and asserts the unrelated run *starts* while the follow-up is still `pending` —
then releases the incumbent and asserts the deferred run was retried rather than
dropped. Plus: three runs deferred at capacity 1 execute in their original order,
and `_try_dispatch` called 25 times requests the stop once.

**Verified against the pre-fix code:** the cross-session test fails with the spin
loop restored. The ordering test does **not** discriminate — the old loop preserved
order too, by blocking — it pins a property the new shape must not lose. The
supersede test likewise pins new behaviour: the dedupe lives in `_try_dispatch`,
which the revert kept.

**Still open, related:** a deferred run whose session incumbent never releases waits
indefinitely. That is correct (it is admitted the moment the slot frees), but there
is no visibility into it — `queue_position` counts pending rows, not why one is
stuck.

**Related leak:** `request_stop` uses `_stop_events.setdefault(run_id, Event())`
(`bridge.py:84-86`), so calling `POST /api/runs/{unknown}/interrupt` creates an
`Event` that is only popped in `run_lea`'s `finally`. A run that never starts
leaves the entry forever. `_session_allowlists` (`bridge.py:248`) is likewise never
cleaned. Both are small, but both are unbounded in a long-lived process.

### X2 — Concurrent runs in one shared project repo race on `git add -A` (Medium)

**Where:** `adapter/app/gitstore.py:96-105`, used from `bridge.py:1182`,
`uploads.py:172, 201, 329`, `projects.py:313, 484`, `filesystem.py:114`

`commit_all` does `git add -A` → `git diff --cached --name-only` → `git commit`.
Project sessions **share one repo** (D24), and up to 4 runs can be admitted at
once. Nothing serializes them. Two failure modes:

1. **`index.lock` contention.** Two concurrent `git add -A` in the same repo make
   one fail with `Unable to create '.git/index.lock'`; `_git` raises
   `GitStoreError`, which in `bridge.py`'s `ToolResulted` branch is unguarded and
   propagates to the outer handler — failing an otherwise-successful run.
2. **Cross-contamination.** `git add -A` stages *everything* in the repo, so run A's
   asset commit includes run B's half-written proof file, attributed to A's commit
   message. Harmless for correctness (SQL owns proof content) but it makes
   `git log` useless as an audit trail, and it's what makes the `.gitignore`
   guard in `ensure_overleaf_gitignore` load-bearing rather than belt-and-braces.

`prover/lea/tools.py:29-38` already has the right pattern — a per-`lake_root` lock
keyed in a dict — for exactly this class of problem.

#### ✅ Fixed (2026-07-24)

Both halves, in `gitstore.py`.

**The crash:** a per-repo-path `threading.Lock` wraps `commit_all`
(`gitstore.py:41-61`). Keyed on the *resolved path* rather than per `GitStore`
instance, because callers construct a fresh `GitStore(proofs_root)` per operation —
an instance-level lock would have guarded nothing. Unrelated repos still commit in
parallel.

**The contamination:** `commit_all` takes an optional `paths`, and the eight call
sites that know what they wrote now pass it — the agent's asset write, the canvas and
filesystem edits, uploads and their sidecars, deletes, the Overleaf mirror subtree,
and artifact retire/restore. Provisioning and namespace migration keep the whole tree,
because there the tree genuinely is the unit of work.

The staging is `git add -A -- <paths>`, not `git add -- <paths>`: **with** a pathspec,
`-A` means "all changes under these paths, *including deletions*". Without it a
removed file's deletion would never be staged, so a delete would silently never be
committed — which is why one of the tests is specifically a deletion.

**Scope, stated honestly:** the lock is in-process. That covers the adapter's own
threads, which is where the concurrency comes from. It does **not** cover the agent
running `git` through the `bash` tool against the same repo — nothing can, short of
taking git's own lock — so that remains a pre-existing, unbounded race. The docstring
says so.

**Tests:** eight threads committing to one repo behind a barrier all succeed (this is
the `index.lock` failure, reproduced); a scoped commit carries only its own file while
a concurrent run's half-written file stays uncommitted on disk; a scoped commit stages
a deletion; unscoped `commit_all` still takes the whole tree; and the lock is shared
per repo, distinct across repos, and stable across differently-spelled paths for the
same repo.

**Verified against the pre-fix code:** the concurrency test and the contamination test
both fail.

**Now more reachable than when first reported:** fixing [X1](#x1) means four runs
genuinely do execute at once, so this race went from theoretical to routine in the
same session.

### X6 — Concurrent startup can fail to migrate (Medium) — *found 2026-07-24*

**Where:** `adapter/app/migrations.py:21-23, 53-70`,
`adapter/migrations/versions/0006_*.py`, `0007_merge_artifact_and_compaction.py`

Found while running the suite for the [C11](#c11) fix:
`test_concurrent_startup_migrates_exactly_once` failed once in ~10 full-suite runs.
It looked like an ordinary flake — it passes in isolation and on rerun — but it is
not. Running ten copies of that one test in parallel reproduced it **4 times out of
10**, with two distinct errors:

```
alembic.util.exc.CommandError: Requested revision 0007_merge_artifact_and_compaction
    overlaps with other requested revisions 0006_artifact_index
```
```
...updating '0006_timeline_compaction_kind' to '0007_merge_artifact_and_compaction'
    in 'alembic_version'; 0 found
```

`migrations.py`'s module docstring claims:

> *Several workers may start at once and all call `upgrade_to_head()`. Alembic takes
> SQLite's write lock for each revision, so the losers block and then observe the
> applied version — exactly-once, verified in `tests/test_migrations.py`.*

That holds for a **linear** chain, which is what existed when it was written. The
graph now branches: `0005_session_parent` has two children (`0006_artifact_index`
and `0006_timeline_compaction_kind`) merged by `0007`. Alembic computes the upgrade
plan from the version it reads *before* taking any lock; the lock serializes the
individual writes, not plan-then-apply. So two processes can legitimately be sitting
on different branch heads, and the merge step's `UPDATE alembic_version` matches
zero rows — or the plan is rejected outright as overlapping.

**Why it matters beyond the test.** `main.py`'s `startup()` calls `init_db()` →
`upgrade_to_head()`, and the exception propagates out of the startup handler, so the
adapter fails to boot. A single uvicorn process never hits it — but the docstring
explicitly designs for "several workers", and the repo's own test spawns four
processes, so the concurrency claim is load-bearing documentation that is now false.
The failure is also *transient and confusing*: a retry usually succeeds, which is
exactly the shape that gets dismissed as flakiness.

#### ✅ Fixed (2026-07-24)

New `migrations._migration_lock()` — an exclusive `flock` on
`<db>.migrate.lock`, beside the database — wraps the **entire** body of
`upgrade_to_head()` (`migrations.py:42-102`, `:121-145`). Reading the current
revision, deciding whether to snapshot, and applying the plan are now one atomic
step, which is the actual requirement: Alembic plans against the version it reads
first, so any split between "read" and "apply" is the bug.

**Why `flock` and not `BEGIN EXCLUSIVE`.** The database-level lock was the obvious
candidate and it doesn't work: Alembic opens its own SQLAlchemy connection, so
holding `BEGIN EXCLUSIVE` on a second connection would lock Alembic out of the very
database it is trying to migrate. The lock has to sit *outside* the database.

**Why blocking, with no timeout.** `flock` is released by the kernel when the holding
process dies, so a crashed migrator cannot strand it. The only thing that makes a
waiter wait is another process genuinely migrating — exactly when waiting is
correct — so a timeout could only convert "someone is still working" into a spurious
startup failure. Windows (no `fcntl`) degrades to the previous unlocked behaviour
with a warning rather than refusing to start; single-process startup there is
unaffected.

**The shortcut I did not take:** linearizing the graph by re-pointing
`0006_timeline_compaction_kind` at `0006_artifact_index` and deleting the merge would
edit revisions already applied in real databases, which `CLAUDE.md`'s own rule
forbids ("never edit an applied one"). The branch is legitimate history; the runner
was what needed fixing.

**Bonus fix:** the snapshot decision moved inside the lock, so N workers racing a
pending migration now take **one** backup between them instead of one each.

**Tests:** `test_migrations.py` — a direct mutual-exclusion test of the primitive (6
processes log enter//exit around a deliberate pause; the log must be perfectly
nested), a test that the lock path follows `db.DB_PATH` at call time rather than
being bound at import (the hazard `backup.py` documents), and a test that a pending
migration produces exactly one snapshot across 6 concurrent workers. The existing
`test_concurrent_startup_migrates_exactly_once` went from 4 to 8 workers — the
failure is a race, so the test is only as good as the contention it creates — and its
docstring, which asserted the wrong mechanism, was corrected.

**Verified:** the reproduction that found this (10 parallel runs of the concurrency
tests) fails **4 out of 10** with the lock removed, with exactly the two documented
errors plus the snapshot-count assertion; **0 out of 30** with it in place.

**Also corrected:** the module docstring's "Alembic takes SQLite's write lock for
each revision … exactly-once, verified in `tests/test_migrations.py`" now describes
the file lock and explains why the database lock is insufficient.

## Performance and scale

<a id="p1"></a>
### P1 — `RunBroker` buffers everything and rescans it 12.5×/second per subscriber (High)

**Where:** `adapter/app/runbroker.py:55-72`, `adapter/app/routes/runs.py:91-102`

```python
def events_after(self, cursor):
    return [e for e in self._events if e["seq"] > cursor]   # O(n), full scan
```

with

```python
pending = broker.events_after(cursor)
...
await asyncio.sleep(0.08)                                   # 12.5 Hz
```

Two compounding problems:

1. **The buffer holds every event for the run's life**, including one
   `assistant_delta` per streamed token *and* every `code_step` payload — which
   carries the **full file contents** (`bridge.py:1097`). A long run over a large
   proof buffers tens of MB; four concurrent runs multiply it. The module
   docstring's justification ("Runs are minutes long; holding their events in
   memory is cheap for this local/single-tenant adapter") is reasonable for
   counts but was not written with per-token deltas and whole-file payloads in
   mind.
2. **The scan is linear and repeated.** `seq` is exactly `index + 1`, so
   `events_after` could be `self._events[cursor:]` — an O(1) slice. As written,
   a 20 000-event run with two attached subscribers performs 500 000
   comparisons per second, in the event loop thread, for a stream that is mostly
   empty.

#### ✅ Fixed (2026-07-24) — partially

Two of the three, and the third deliberately left alone.

**The rescan.** `events_after` is now `self._events[cursor:]`
(`runbroker.py:68-85`). `seq` is assigned as `len(self._events) + 1`, so it *is* the
1-based index and the filter was computing something it already knew. The cursor is
clamped to `[0, len]` rather than trusted: it arrives from a client-supplied
`Last-Event-ID`/`?since=`, and a raw negative index would have silently re-sent the
tail of the buffer — a hazard the filter form didn't have, introduced by the slice
and closed in the same change.

**The frame flood.** A new `bridge._DeltaStream` batches streamed text into roughly
one frame per subscriber poll (`bridge.py:345-405`). The interval is
`_DELTA_FLUSH_SECONDS = 0.08`, matching `_subscribe`'s poll: text produced between
two polls is delivered together no matter how many frames carried it, so finer
granularity was never observable. A slow stream is not delayed — the deadline is
checked on arrival, so tokens arriving slower than the interval flush immediately.
The same batching applies to sub-agent children, which stream onto their own brokers
identically.

Two things make this safe:

- **Frames are merged before publication, never after.** An event already in the
  broker carries a `seq` a subscriber may have consumed, so appending to it in place
  would silently lose text for any client whose cursor is already past it. That rules
  out compacting the buffer, which is why the batching is upstream.
- **Ordering is enforced in one place.** `run_lea` flushes the batch on any event
  that isn't an `AssistantTextDelta`, as a single check right after `gen.send`, rather
  than a flush in each of the fifteen branches — so the rule can't be forgotten when
  a new event type is added. The `finally` flushes too, so a run that dies mid-batch
  still publishes its last words before `done`.

**Not done — the code-step payloads.** Streamed `code_step` events still carry the
file's full bytes, which is the larger memory term. That is deliberate: "the streamed
SSE payload and the stored row carry the **same bytes**, so the live canvas and a
reload can't disagree" is a stated architectural invariant (`CLAUDE.md`, `bridge.py`
header). Replacing the payload with a row id would trade a documented
can't-disagree property for a fetch that can fail — the exact shape of the hydrate
bug v2.3 removed. The remaining exposure is a long run over large proofs; if it
bites, the answer is bounding the buffer with an explicit replay-from-DB path, not
quietly weakening the invariant.

**Tests:** `test_runbroker.py` — exact tail semantics at several cursors, hostile
cursor clamping, and a concurrent publish/replay test asserting no reordering or
duplication. `test_bridge.py` — seven tokens across a tool call produce fewer frames
but the identical concatenated text, with everything narrated before the tool call
published before it; plus a run that raises mid-batch still emitting its text before
`done`.

**Verified against the pre-fix code:** the batching test fails (7 frames for 7
tokens). The clamping and trailing-flush tests do *not* discriminate — the old filter
tolerated negative cursors and per-token emission was trivially ordered; they pin
properties of the new implementation rather than reproducing the old bug.

<a id="p2"></a>
### P2 — `check_spend_cap()` runs the full usage aggregate on every `UsageUpdated` (High)

**Where:** `adapter/app/bridge.py:957-975`, `:1139-1145`

```python
persisted = float(store.usage_stats()["global"]["cost_usd"])
```

called from `check_spend_cap`, which fires on **every `UsageUpdated` event and
every `TurnStarted`**. `usage_stats()` is not cheap: it runs `_list_sessions` — a
100-row aggregate with six correlated subqueries per row, including two that scan
`timeline` — plus two more GROUP BY aggregates over `runs`.

With four concurrent runs each emitting usage per model call, this is several
heavy queries per second against a single-writer SQLite database that is
simultaneously taking `BEGIN IMMEDIATE` write locks for every message and code
step. It is a self-inflicted contention source of exactly the kind
`get_run_status` was introduced to eliminate (`store.py:1006-1013`).

#### ✅ Fixed (2026-07-24)

Two steps, one in each of two commits. [C1](#c1) replaced `usage_stats()["global"]`
with the scalar `store.total_spend_usd()` — which was the correctness fix and removed
the six correlated subqueries. This finishes the job: `bridge._persisted_spend_usd()`
memoizes that scalar for `_PERSISTED_SPEND_TTL_SECONDS = 2.0`
(`bridge.py:409-448`).

The TTL doesn't weaken the cap, and the reason is structural rather than a judgement
call: **persisted spend only changes when a run finishes.** The term that moves
continuously *within* a run is the in-memory `_live_run_costs` overlay, which is
untouched and always exact. So the staleness this admits is bounded by another run
finishing inside a 2-second window — while the check itself went from several DB
aggregates per second per active run, against the same single-writer SQLite the runs
are writing to, to one read per window.

**One bug found by its own test.** The first version keyed the cache on time alone,
and the full suite failed while the test passed in isolation: a module-level cache
handed one test's total to the next. The cache is now keyed on `db.DB_PATH` as well —
the total is a property of *one* database, and production never repoints that path,
so this costs nothing and is simply correct. It is the same hazard `backup.py`
documents for the path it copies. `reset_persisted_spend_cache()` is exported for
tests and for any caller that has just persisted a cost and wants it seen now.

**Tests:** `test_bridge.py` — a capped run emitting 60 usage events across 3 turns
makes **one** database read for 63 cap checks; the cache is scoped to its database;
and the primitive reads once per window across 50 calls.

**Verified against the pre-fix code:** with `check_spend_cap` reading the store
directly, the end-to-end test reports 63 reads instead of 1.

<a id="p3"></a>
### P3 — `session_detail` and `build_graph` are N+1 with a new SQLite connection per blob (High)

**Where:** `adapter/app/store.py:1234-1240` (`blob_content`), `:1265-1291`
(`_code_step_from_row`), `:1619-1623`; `adapter/app/graph.py:151-166`

`session_detail` reads the whole timeline inside one connection, then builds the
response *outside* it:

```python
code_steps = [_code_step_from_row(r) for r in rows if r["kind"] == "code"]
```

and `_code_step_from_row` calls `blob_content(...)`, which opens **its own
connection** (`with connect()`), executes one SELECT, and closes it. A session with
200 code steps opens 200 SQLite connections and materializes 200 full file
contents — to render a thread the UI mostly scrolls past.

`graph.build_graph` is worse: for each blueprint node it calls
`code_steps_for_project_path`, which returns *every* step for that file across the
project, each hydrating its own blob through its own connection — and then uses
only `steps[0]["check_status"]` and the session ids. A 30-node blueprint with 20
revisions per file is 600 connections and 600 full file reads per `/graph` request,
and the Overleaf pane polls `/graph`.

#### ✅ Fixed (2026-07-24)

A shared `store.TIMELINE_WITH_BLOB` select (`store.py:1271-1280`) left-joins
`artifact_blobs`, so the bytes arrive **with** the row. `_code_step_from_row` prefers
that joined value, falling back to the old per-row `blob_content()` lookup only when
a query didn't use the join — so no caller breaks, and any that still pays the old
cost is doing so visibly. Every code-step read now goes through it: `session_detail`,
`latest_code_step_for_path`, `latest_agent_code_step`,
`latest_agent_code_step_for_path`, `set_code_step_check`, and
`code_steps_for_project_path`.

The column is aliased `blob_content` because **`timeline.content` already exists** —
it holds message text — so a bare `b.content` would have collided and silently
shadowed one of them. `_code_step_from_row` strips the alias from the row it returns,
so the API shape is unchanged.

**The graph.** `code_steps_for_project_path` takes `include_content=False`, and
`graph.build_graph` passes it (`graph.py:151-160`). The graph reads only
`check_status`, `session_id`, and `created_at`, so hydrating every historical revision
of every file — each formerly its own connection and its own full copy of the proof —
was work whose result was thrown away. This is the endpoint the Overleaf pane polls.

**Not done:** paginating `session_detail`'s timeline. It now costs one query instead
of N+1, which is the structural fix; capping how much history a single response
carries is a separate API-shape decision.

**Tests:** `test_store.py` — the anchor asserts **connections opened**, not elapsed
time (the defect was structural, so counting the structure is deterministic in CI and
is what regresses): `session_detail` over 40 steps opens fewer than 15 connections
where it previously opened ~40 for the blobs alone, with the content still complete;
each single-row code-step read costs exactly one connection; the graph's
content-free read returns verdicts and attribution byte-identical to the full read
while withholding only the bytes it never looks at; and the check back-fill still
returns its row's content, so a verdict landing on a step can't blank the canvas.

**Verified against the pre-fix code:** 3 of the 4 fail — `session_detail` at 40+
connections and the single-row reads at 26.

<a id="p4"></a>
### P4 — Two polling SSE endpoints hold per-client DB query loops for up to 3 hours (Medium)

**Where:** `adapter/app/routes/runs.py:105-116` (`_passive_done`),
`adapter/app/routes/sessions.py:63-101` (`session_list_events`)

- `_passive_done` loops 36 000 times at 0.3 s (3 h), calling `store.get_run` — one
  connection open/close — each tick. Every browser tab that reattaches to an
  already-finished run gets one of these.
- `session_list_events` loops 10 800 times at 1 s, calling `sessions_digest()` per
  tick, per connected client.

Neither is wrong, but together they establish a floor of several SQLite
connections per second per open tab, against the same single-writer database that
runs are writing to. The digest design is good (cheap fingerprint, expensive query
only on change) — the cost is the polling itself.

#### ✅ Fixed (2026-07-24)

Exactly the shape the finding proposed, for both endpoints.

**The session feed** now checks `store.sessions_change_token()` — an in-process
counter bumped by every write that can move the list — and only runs the SQL digest
when it moves, or every 30 ticks as a backstop. An idle client costs an integer
comparison instead of a query per second. The backstop matters: the token only sees
writes from *this* process, which is all of them today, so if that ever stops being
true the feed degrades to the old latency rather than to silence.

**The passive observer** backs off (0.3s × 30 → 1s × 60 → 3s), keeping the same
worst-case horizon for roughly an eighth of the queries. The overwhelmingly common
case settles on the first read, so the fast phase is what actually matters.

**Tests:** the token moves on create/run/update and not on reads.

<a id="p5"></a>
### P5 — `artifact_blobs` are only garbage-collected inside project deletion (Low)

**Where:** `adapter/app/store.py:552-556`

The orphan sweep runs only in `delete_project_cascade`. Loose sessions have no
delete path that touches it, and `upsert_user_code_step`'s coalescing explicitly
drops references to superseded blobs — so every debounced autosave that produced a
unique intermediate state leaves a permanently unreferenced blob holding a full
copy of the file.

Content addressing bounds duplicates, not orphans. Over months of editing this is
the fastest-growing table in the database, and the database is now the thing
`backup.py` copies on every migration.

**Fix:** run the same orphan sweep on session delete and on a periodic/startup
vacuum step.
