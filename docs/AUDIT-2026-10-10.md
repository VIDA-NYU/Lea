## Findings

| ID | Priority | Confirmed behavior |
| --- | --- | --- |
| F1 | P1 | An agent check can certify different bytes from those Lean checked. |
| F2 | P1 | Editing an imported theorem leaves a broken dependent theorem `proved`. |

### F1: Agent checks certify unchecked replacement bytes

**Locations:** [bridge.py](../apps/lea-standalone/adapter/app/bridge.py), lines
2237–2279; [agent.py](../apps/lea-standalone/prover/lea/agent.py), lines 418–467
and 1336–1476.

The bridge records an agent's `CheckResult` without comparing the compiler's
`execution.content_sha256` with the stored snapshot. If there is no previous
step, it reads the current file and assigns the completed check to those bytes.
The agent's final verification gate tracks paths and explicit write tools, but
does not detect a subsequent `bash` edit.

In ordinary tool execution, meaning events are emitted after the turn's tools
have executed. A single turn that writes a valid proof, checks it, then uses
`bash` to replace it therefore stores the replacement with the earlier success.
The final gate does not request another check.

**Reproduction:** [repro_agent_revision.py](audit-2026-10-10/repro_agent_revision.py)
runs the actual agent, tools, bridge and persistence with scripted model output
and a real Lean compiler. It writes `True := by trivial`, checks it, then
replaces it with `False := by trivial` through the shell. Results:

```text
stored_code_is_bad: true
stored_check_status: ok
run_status: proved
formalization_status: proved
actual_final_check: error
```

The compiler's checked hash and the stored hash differ. Full output:
[agent-revision.json](audit-2026-10-10/agent-revision.json).

**Fix:** Bind agent verdicts to immutable checked content, reject mismatched
hashes in both bridge branches, and compare current bytes against checked bytes
at the agent's final gate. Cover shell mutations, batched tools and delayed
events. The previous audit's manual-check revision protections do not cover
this agent-event path.

### F2: Dependency edits preserve stale successful evidence

**Locations:** [proof_files.py](../apps/lea-standalone/adapter/app/proof_files.py),
line 126; [formalizations.py](../apps/lea-standalone/adapter/app/formalizations.py),
lines 69–144; [routes/projects.py](../apps/lea-standalone/adapter/app/routes/projects.py),
lines 389 and 827.

Saving a shared file clears legacy `safe_verify_status`, but does not invalidate
dependent Lean checks. Formalization validity checks the target's own revision
and source statement; it does not track the imported environment. A dependent
file whose bytes have not changed can remain `proved` with `check_current=true`
after an import changes incompatibly.

**Reproduction:** [repro_dependency_revision.py](audit-2026-10-10/repro_dependency_revision.py)
creates two genuinely compiling modules and seeds their successful-run records.
It renames an upstream declaration through the actual project save route. The
edited module passes its check. After rebuilding that module, the dependent
module fails with `Unknown identifier base`, while the target-status API still
returns:

```text
downstream_status_after_rebuild: proved
downstream_check_current: true
actual_downstream_check: error
formalization_status: proved
```

Full output: [dependency-revision.json](audit-2026-10-10/dependency-revision.json).

**Fix:** Track imported dependency revisions or invalidate dependent evidence
centrally when sources change. Mark affected targets unchecked until checked
against the current dependency environment. This must cover the Filesystem
editor and backend callers as well as extension cascade workflows.

### F3: Substring classification reverses conservative outcomes

**Location:** [agent.py](../apps/lea-standalone/prover/lea/agent.py), line 295.

`_parse_result_kind` tests whether the response contains `DISPROVED` or `PROVED`
before considering `NEEDS_REVIEW`. Although the prompt requests a single enum
token, a provider response containing prose or negation is accepted:

```text
NOT PROVED                         -> proved
NEEDS_REVIEW: this is not PROVED    -> proved
The original theorem was not
disproved. PROVED                   -> disproved
```

This classifier determines whether a compiling artifact answers the user's
mathematical request, so accepting a negated success bypasses that review gate.
See [repro_classifier.py](audit-2026-10-10/repro_classifier.py) and
[classifier.json](audit-2026-10-10/classifier.json).

**Fix:** Accept exact enum values only. Treat nonconforming or contradictory
output as `needs_review`.

### F4: CLI/container shutdown wedges the adapter

**Locations:** [runtime.py](../apps/lea-standalone/adapter/app/runtime.py), line
171; [docker/entrypoint.sh](../apps/lea-standalone/docker/entrypoint.sh), line 14;
[main.py](../apps/lea-standalone/adapter/app/main.py), line 94.

Draining changes lifecycle state to `stopping`, but exits only when a server was
registered with `runtime.bind_server`. The custom `run_api.py` launcher binds
it; the container starts `python -m uvicorn app.main:app`, which does not.
Consequently shutdown/restart completes its drain without exiting or resuming
admission. Health continues to return `ok=true`.

**Reproduction:** [repro_cli_restart.py](audit-2026-10-10/repro_cli_restart.py)
starts a real isolated server using `uvicorn.run`, the same unbound lifecycle
path as the CLI. With no active work, a shutdown request produces:

```text
state_after_shutdown: stopping
health_ok: true
process_still_running: true
new_run_http_status: 503
```

Full output: [cli-restart.json](audit-2026-10-10/cli-restart.json).

**Fix:** Use a consistently bound launcher across local and container starts,
including configurable bind address and port. Make readiness reflect admission
state and add a real-process restart/shutdown regression. Incoming VIDA main's
container launcher also uses the CLI, so preserving it alone will not fix this.
