LeaUI v2.4 — Error Transparency COMPLETE

Every failure gets an owner in the UI · audit of all 88 except sites across adapter + prover + frontend · follows v2.3.1-subagents-visibility-parallelism-progress.html
v2.3.1 made the agent's work visible (live children, first-class child runs, compaction markers). This one makes its failures visible. The audit finding is blunt: the error model is one mutable string — proofSession.error?: string (proofSession.ts:65) rendered as a single <div class="err-banner"> (ChatThread.tsx:538). Last-writer-wins, never persisted, no severity, no source, and no link to the turn, tool, or step that failed. Its main producer is bridge.py:1101 — f"{type(exc).__name__}: {exc}", a raw Python exception as user-facing copy. The through-line: replace the banner with an anchored, persisted, coded Diagnostic that renders where the failure happened — the generalization of the one surface that already works, the red sub-agent child.

What the audit found

Error is dead code. events.py:86 defines it and bridge.py:1064 handles it → run_error. grep -rn "yield Error" prover/lea/ returns nothing. The prover has no way to report a recoverable failure as an event — everything is a raised exception caught by one outer except, or a string handed to the model. · Tool failures are visible to the LLM and invisible to the human: agent.py:886 turns every tool exception into f"Error: tool '{name}' raised …" — a tool_result the model reads and may silently recover from. The human sees only the Running <tool> chip. · ~28 of 88 except blocks swallow silently (pass / default-and-continue) across uploads, graph, projects, ghimport, models_catalog. · A failed proof promotion is a logger.warning (bridge.py:653) — children run, nothing is promoted, the user is told nothing. · Nothing is persisted: "what went wrong in yesterday's run" exists only in a terminal's stderr.

Design calls

A failure needs an owner, not a banner. One global string means the second error erases the first, and a failure three turns back is unattributable. Every diagnostic carries a context (run_id, turn, tool, path, child_id, call_id) and renders at that anchor — on the tool step, the code card, the child row.
Three severities, three shapes. fatal → terminal run state + a persisted timeline row. step_error → inline on the step it belongs to; the run continues. degraded → a persistent capability indicator, not a transient toast, because it describes an ongoing state (LSP fell back to cold compile, SafeVerify unavailable, overrides didn't load). A toast is the wrong shape for a condition that is still true five minutes later.
Coded, with a remedy. provider.auth_missing → "No ANTHROPIC_API_KEY. Add one in Settings." Codes are testable and let a remedy be attached once; raw exception strings are neither. AuthenticationError: … is a stack-trace fragment, not an instruction.
Persisted, because a diagnostic is history. Stored as kind='diagnostic' on timeline, reusing the data JSON column that already exists and is essentially unused (0003_timeline_and_blobs.py:133 — "JSON: per-tool specifics only"). Same principle as the compaction marker (G3): live and reload must not disagree.
"Couldn't do it" ≠ "it's wrong." Already the right call in VerifyResult (events.py:72), which keeps error/unavailable distinct from rejected. Generalize that discipline: a swallowed OSError currently makes a partial import, graph, or file inventory present itself as a complete one.
Composes with the tool-descriptor refactor, doesn't compete. Once a handler returns structured effects instead of a bare str, tool.raised becomes a declared failure effect rather than prose only the model reads — and _meaning_events's string-sniffing (agent.py:335) goes away with it. Phase A here is deliberately buildable before that refactor, and makes it cheaper.

What already works — the patterns to copy

The red sub-agent child (_subagent_error, bridge.py:517) — a failure rendered on the thing that failed, with its real cause, not a paraphrase. This is the template for the whole phase. · VerifyResult's tri-state — ok/rejected/error/unavailable, with "couldn't verify" explicitly never reading as "verified bad." · The persisted pending approval (bridge.py:164) — an interactive prompt that survives a stream drop and a session switch because it lives on the run row, not only in a one-shot SSE. · Honest capacity 409s (runs.py:324) with Retry-After and human copy, and the 402 spend-limit message. These four are already right; the work is making everything else behave like them.

X2 Unplanned — found in live testing: a child sat "Checking with Lean…" after finishing

Every child was reported finished at the same instant, whenever the SLOWEST one finished. run_children_concurrently returns only when all children are done, and the coordinator drained every SubagentFinished after it returned — so a child that finished in 15s kept status='running' for another 40s, and its session view showed a live spinner over a completed transcript. The DB was unambiguous: 8 children created within the same second, all retired within 30ms of each other, ~51s later. Fixed by emitting each child's result as it finishes. Pinned by a timing test (fast child + blocked sibling) that was verified to FAIL without the fix — the first two revert attempts printed nothing at all, which looked like "passes either way" until it turned out an earlier test was crashing the runner before it ran. Pre-existing E2 behaviour from v2.3.1; invisible at 2 children, obvious at 8.

X3 Unplanned — found in live testing: a running child's task was invisible

The delegated prompt only existed in the child's transcript, which replays on FINISH. So a running child's session was empty and its three-word title was the whole visible record of what it had been asked to do — you could watch it work for minutes with no way to judge whether the coordinator had delegated the right thing, which is exactly the window in which that judgement is still worth making. SubagentStarted now carries the full task; the adapter records it as the child's first message at spawn (and skips the transcript's leading user message on finish, so it isn't stored twice); the session list exposes it beside final_summary. Also fixed alongside: an expanded running child said "This sub-agent produced no final output" — a verdict, and a false one, since an unfinished run has no output yet.

X1 Unplanned — found by a test this work turned green

A DENIED write_file emitted FileChanged. tests/agent/test_gate.py had two failing assertions on main ("denied → NOT executed"). Cause: _meaning_events decides whether a write succeeded by sniffing the result string — _tool_result_ok is "non-empty and doesn't start with error:" — and the decline notice satisfies that. So refusing a write still emitted FileChanged, and the adapter dutifully read the path and recorded a code step for a write the user had just refused. Fixed by tracking refused call indices in the loop (refused_idx) instead of re-deriving a refusal from prose — the loop knows it denied the call. Both assertions now pass. This is the string-sniffing failure mode in miniature, and the reason the tool contract is the next thing worth changing.

What to exercise when you test

Start a run with no API key → one fatal card naming the provider + "add a key in Settings", not AuthenticationError: · Stop while an approval card is up → "Stop cancelled the pending approval"; the agent must NOT say you declined it · Spawn 6+ sub-agents in one turn → children 6+ read queued, not exploring · Let a sub-agent hit its turn budget → the child row says so instead of looking like a clean finish · Delegate, then let the winner fail re-verification → a card naming the candidate and why · Reload mid-thread → every card is still there, in the same place · Kill the LSP daemon → an amber "Lean checks are running cold" strip that stays up.
Known deviations from the plan, deliberate: (1) A4's catalog is resolved server-side — title/remedy ship on the wire — rather than duplicated as a second frontend catalog, so there is exactly one source of copy. (2) G2 needed no schema change: a run's failure surfaces as its persisted fatal diagnostic rather than a new column on runs. (3) Request/ response endpoints (graph, rename, upload, models) can't stream, so they return the same payload in a warnings[] array — one shape, two transports.
