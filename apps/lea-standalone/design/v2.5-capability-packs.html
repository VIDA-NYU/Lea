Part 1 — The Plan
The goal: let a mathematician — not a programmer — extend the prover with their own procedural knowledge, their own specialist sub-agents, and third-party tools. Three asks came in separately (skills, custom agents, one-click MCP) and a fourth followed (multiple API keys, custom tools, guided prompt authoring). They are one feature: a capability pack. The audit finding is that most of the machinery already exists — skills are fully shipped, MCP is fully implemented in the prover and simply never wired to the adapter, and the multi-key secret vault already accepts arbitrary *_API_KEY entries. What is missing is the declaration layer that ties them together, and one small prover change without which user-defined sub-agents cannot work at all.

Already shipped — do not rebuild

Single-file skills are done end to end. DB-backed rows with full CRUD plus GitHub import (routes/skills.py), global ∪ per-project scoping (D47), materialized to per-run temp .md files (skills_catalog.py) and fed to the prover as cfg.skills (bridge.py:1722). SkillFactory.tsx is the UI. Multi-file skills are not supported at all — see gap 4 below, found by importing a real one. · MCP is complete in the prover. lea/mcp.py handles stdio / SSE / streamable-HTTP, registers discovered tools into the per-activation registry overlay, and fails soft per server; agent.py:572 starts it whenever cfg.mcp_servers is non-empty. · The multi-key vault already generalizes. config.py:98 matches any [A-Z][A-Z0-9_]*_API_KEY root entry, _export_provider_keys (config.py:124) publishes them to os.environ and retracts them on clear, and SettingsPage.tsx:49 already renders user-added key rows. mcp.py:115 merges a server's env over os.environ, so a server inherits saved keys for free. · The registry is the right seam. register(..., scoped=True) into the activation overlay (registry.py) is exactly how a declarative custom tool should register — same path MCP uses, vanishes on run exit.

The three real gaps

1 · The adapter never sets cfg.mcp_servers. Zero references anywhere in adapter/app/. The prover side is finished and unreachable — the only way to enable an MCP server today is the CLI with a hand-written YAML file. Your own comments already call this out as planned-not-built: stores/factories.ts:14 and ScopeAssignment.tsx:6 both say "the (deferred) MCP Factory."
2 · Sub-agent roles cannot be created, only retuned. profiles.py:64 globs only the vendored lea/agents/*.yaml (two files), and routes/subagents.py is GET + PUT with no POST or DELETE. A user can change proof-candidate's model; they cannot add counterexample-hunter.
3 · LOAD-BEARING The coordinator is never told which roles exist. _SPAWN_SCHEMA (subagents.py:64) declares subagent_type as a free-text string, with role names mentioned only in English prose, and it is registered at import time (subagents.py:646). With two hardcoded roles that survives. The moment a user creates a role, it breaks silently: the model has no way to learn the role exists, so it never calls it — and no error is raised either. The user configures an agent and simply nothing happens. Every other slice in Phase B is decorative until the spawn schema is built per-run with an enum of available roles and their descriptions.

Why the wrong file won. _locate_md (ghimport.py:177) tries SKILL.md → README.md → first *.md. But the first two go through _find_ci, which iterates base.iterdir() — direct children only. This repo's SKILL.md is four levels down, so it is invisible; README.md sits at the root and wins. The rglob fallback would have found it, but only runs when neither priority name exists at the root. Any repo with a root README loses its real skill.
And fixing the lookup is not enough. A skill here is a directory, not a file: SKILL.md links references/*.md (including anchors like disprove-engine.md#implementation-status) and expects them to be read on demand — the Agent Skills progressive-disclosure model. Lea's model is one body TEXT column → one temp .md → injected wholesale into the system prompt. The references are ~690 KB ≈ 170k tokens; they cannot be concatenated into a prompt, and MAX_BODY_BYTES (256 KB) would refuse them anyway. Every relative link in the imported body is currently dead.
Frontmatter is injected raw. load_skills (lea/skills.py) reads the file and wraps it under ## Skill: <stem> with no parsing, so SKILL.md's YAML (name:, description:, license: MIT) would land verbatim in the system prompt — and its description is precisely the when-to-use text Phase C wants to use.

Where a multi-file skill must live — the read sandbox decides it

The materialization location is not a tidiness question; it is forced. _readable_roots (tools.py:162) allows a run to read exactly two places: its working_dir and the enclosing Lake root (the latter so Mathlib stays readable after search_mathlib returns paths under .lake/packages/mathlib/). Everything else is refused with "outside this run's workspace." That sandbox was added deliberately — reads previously reached ~/.ssh/id_rsa and config/lea.local.toml, which holds every provider key in plaintext, and the autonomous Overleaf path has no approval gate between a prompt-injected instruction and a tool call.
So today's temp dir cannot work for progressive disclosure. skills_catalog materializes to the system temp area — deliberately outside any project repo, so skills never pollute the git-owned tree (D7/D8). That is correct today precisely because the body is injected into the prompt and never read from disk. The moment references are read on demand, every one of those reads is refused.
Two options — and reading OpenHands changed the answer. (a) Copy into <working_dir>/.lea/skills/<slug>/. No sandbox change; .lea/ is the established home for run-adjacent non-proof material and bridge.py:851 already excludes it from formalization attribution. But it is N copies (one per project), and sub-agents may not be able to read it: a child's working_dir is its scratch dir (<wd>/.lea/tmp/<run>/<agent>), so its roots are [scratch, lake_root] — the parent's repo is reachable only if the session repo happens to sit inside the Lake root.
(b) One shared read-only cache + a third readable root. Materialize once (content-addressed), point _readable_roots at it. This is what OpenHands does — SkillResources.skill_root is an absolute path into ~/.openhands/cache/skills, referenced in place, never copied per session. They can do that because they have no read sandbox; Lea does, so the equivalent is a third root.
REVISEDPrefer (b). The earlier draft of this plan recommended (a) on the grounds that widening a just-hardened boundary buys nothing. That was wrong on the facts: (b) buys the sub-agent case by construction — every child gets the same extra root regardless of its working_dir, so the layout dependency above simply disappears instead of becoming a VERIFY item. It is also one copy rather than N, and it matches the reference implementation. The widening is narrow and defensible: a directory Lea creates, holding only materialized skill files, mounted read-only — not a user-supplied path. Writes stay confined by _sandboxed_write_path, untouched.
Either way, materialize per skill-version, not per run. Skills are read-only reference material. Key the cache on content hash and refresh when the row changes; keep the D45 principle that the DB row, not the directory, is the source of truth.

Reference implementation — OpenHands agent-SDK openhands/sdk/skills/

Read from source (clone at ~/Desktop/code/software-agent-sdk, @68aa583, 2026-07-20). It implements the AgentSkills standard that lean4-skills is written against, so this is the format we are consuming — adopt it rather than invent a manifest.
Two injection modes, chosen by format — this corrects H3. Their Skill docstring is explicit: an AgentSkills-format skill is "always listed in <available_skills> with name, description, location" and the "agent reads full content on demand (progressive disclosure)"; a legacy skill with no trigger puts "full content in <REPO_CONTEXT>, always active." Even SKILL.md is not injected — only name + description + location. The earlier plan here proposed injecting the 29 KB SKILL.md; that is unnecessary, and at N skills it would not scale. Lea's existing small always-on skills map exactly onto the legacy mode, so today's behavior is unchanged and the new mode applies only to imported multi-file skills.
Triggers are a whole axis we had not considered. KeywordTrigger / TaskTrigger / PathTrigger (skills/trigger.py): content auto-injects when the user's message matches keywords or a touched file matches a path glob, and disable_model_invocation hides a skill from the listing so it is trigger-only. Directly useful here — a measure-theory skill that fires on the statement text, a Mathlib-style skill that fires on touching a .lean file.
Skills already declare MCP servers — the pack idea is standard, not ours. Skill.mcp_tools: dict[str, MCPServer], loaded from a .mcp.json inside the skill directory (find_mcp_config / load_mcp_config). Plus allowed_tools — a pre-approved tool list, an AgentSkills standard field. So E1's manifest should be the AgentSkills format, and F1/H6's tool lists have a standard home.
Details worth stealing. Precedence public → user → project, later wins (maps onto D47's global ∪ assigned) · description capped at 1024 chars and truncated with a notice pointing at the source path · pinning detected as detached HEAD (tag or SHA) in is_skills_repo_pinned — a concrete mechanism for A6's supply-chain concern · SkillResources models scripts/ / references/ / assets/ explicitly rather than globbing.

The warm-up does not survive a run boundary. In the UI each user message is a run, so an MCP-enabled interactive session pays ~35 s of dead time per message. Where setup actually hurts — all UX, none of it privilege

The useful error never reaches the user. Pointed at a non-Lean directory, the server's own message is excellent and actionable: 
ValueError: Lean project path '/Users/shaswatpatel' must contain `lean-toolchain`
           and either `lakefile.lean` or `lakefile.toml`.
But it dies in the subprocess's stderr. What mcp.py:36 prints — also only to stderr, which no UI user ever sees — is: 
[mcp] server 'lean-lsp' failed to start: Connection closed; continuing without its tools
The run then proceeds with tools=0. A silently degraded run that looks like the feature just does nothing. A typo'd command behaves identically ([Errno 2] No such file or directory: 'uvxx').
44 s of silence on the first call. With no UI affordance that reads as a hang, and it lands precisely when the user is deciding whether the feature works at all.

How OpenHands handles MCP — and the one lesson that lands on A1

They largely don't make it easy. frontend/src/routes/mcp-settings.tsx is a raw CRUD form over the protocol fields — type (sse/stdio/shttp), command, args, env, url, api_key, timeout. No catalog, no one-click, no preflight. A mathematician would be exactly as stuck there as anywhere else. So the curated-catalog plan is not reinventing something the reference implementation solved — it is genuinely ahead of it.
The real "make it easy" answer is bundling, not better forms. A .mcp.json inside a skill directory means installing the skill brings its servers. That is the whole one-click story, and it is what E1/H8 already describe. Their settings form is the advanced door, not the front door.
Worth copying — MCPErrorCollector (openhands/mcp/error_collector.py): a thread-safe collector recording server_name, server_type, error_message, exception_details at each failure site in mcp/client.py, instead of printing to stderr and losing it. Surfaced in the CLI welcome line as "✗ MCP errors detected (type /mcp → select View errors)". This is A3 with a working reference. Note the limits: it is startup-scoped, and the surfacing shown is CLI-only — their web path is no better than Lea's today, so copy the collector, not the reach.
Also worth noting. Their config shape is {"fetch": {"command": "uvx", "args": […]}} — identical to Lea's cfg.mcp_servers, so our format is already the de-facto standard; don't diverge. · api_key is a first-class field on sse/shttp servers. · filter_tools_regex on the agent filters the toolset after MCP tools are added — their answer to tool bloat. Lea's explicit tools: list[str] allowlist is better for auditability, but a regex handles <server>__* wildcards that an explicit list cannot.

LANDS ON A1An MCP spec is secret-bearing — Lea acquires this bug the moment A1 ships

OpenHands removed skills[].mcp_tools from the agent profile (#4017) for exactly one reason, recorded in profiles/agent_profile.py:421: the profile must carry no secret-bearing field, and an embedded MCP config does — because a server spec's env holds API keys. Their disabled_skills deny-list deliberately holds only names.
Lea has the identical exposure, latent. LeaConfig's docstring promises the object "holds no secrets and is safe to log or serialize" — and mcp_servers is a field on it. A1 wires that field. The first catalog entry whose env carries a real key silently breaks the invariant, and every place that logs or serializes a config becomes a key-disclosure site.
CORRECTEDThe fix was NOT free — the earlier draft of this plan had the mechanism backwards, and measuring it found a live leak instead. This block previously claimed a server "inherits" a key with no env entry because mcp.py merges env over os.environ. Both halves were wrong. Measured with a purpose-built echo server:
SpecWhat the child actually received
no env8 vars — HOME, PATH, SHELL, TERM, USER… · no API keys, so nothing is "inherited"
any env entry54 vars — including ANTHROPIC_API_KEY, GOOGLE_API_KEY, OPENAI_API_KEY, GEMINI_API_KEY
The SDK's default is a deliberate allowlist (get_default_environment()), so nothing is inherited; and the old {**os.environ, **cfg_env} — written to stop a bare env stripping PATH — handed the child every credential this process holds. The vendored configs/lean-lsp.yaml sets LEAN_PROJECT_PATH, so it took that branch. An MCP server is third-party code; that was a real leak, not a hypothetical one.
Shipped fix (A7). _child_env now builds: SDK safe base (keeps PATH) + the spec's literal env + the host values of names listed in a new env_from. A server gets what it declares, not the keyring. env_from is what lets a spec name a credential without carrying it — so the rule survives intact, it just needed building: a stored spec may name a key, never carry one.

Design calls

One pack, not three factories. A pack = optional MCP server + optional declarative tools + skill + sub-agent role + requires_keys. This is not aesthetic tidiness: enabling lean-lsp-mcp raw makes the prover worse, because it adds tools that overlap what Lea already has (lean_leansearch/lean_loogle vs search_mathlib; lean_run_code/lean_build vs lean_check). The unit that is safe to one-click is server + recommended tool subset + a skill that teaches their use — which is exactly what the existing configs/lean-lsp.yaml already bundles by hand.
Preflight, not an LLM setup wizard. All three failure modes are deterministically checkable and were verified as such in a few lines of script: (1) is uvx on PATH, (2) does the path contain lean-toolchain + a lakefile, (3) trial-start and capture the child's stderr. A wizard would be non-deterministic, slower, and would still need these same checks to know whether it had succeeded. Reserve the LLM for translating a preflight failure into plain language — never for performing the setup. Auto-filling the path from the workspace the adapter already knows deletes failure mode (1) outright.
Authoring and consuming are different roles. A mathematician cannot write an endpoint spec with a params schema — that is still engineering. But they can absolutely write when to use this and when not to. So the endpoint spec is authored once (by us, shipped in the curated catalog, or imported from GitHub exactly as ghimport.fetch_skill already does for skills), and the prompt fields are what the mathematician owns and edits. This split is what makes "custom tools for non-programmers" coherent rather than a contradiction.
One guided form, three consumers. General description / when to use / when not to use / procedural notes. The fields compile into one string through a fixed template, because build_toolset hands the model nothing but schema["description"]; store the fields separately so they stay editable, render deterministically. "When not to use" is load-bearing, not decorative — it is the mitigation for tool overlap, and for a sub-agent role it is what stops a coordinator delegating everything. For roles, the same text populates the enum descriptions in the dynamic spawn schema: writing "when to use this" and making the coordinator pick correctly are the same act.

Secrets: declare the name, never the value. The vault exists; what is missing is requires_keys: ["WOLFRAM_API_KEY"] on the manifest. That one field buys: prompt for the key at enable-time, block enabling until it is set, and warn "clearing this breaks 2 enabled packs." The pack spec stores the key name; the handler resolves from os.environ at call time. LeaConfig's docstring promises it "holds no secrets and is safe to log or serialize" — a tool spec that inlined a key would quietly break that, and tool schemas are transmitted to the model provider.
The real security risk is supply chain, not privilege. uvx lean-lsp-mcp downloads and executes code from PyPI at every run start, unpinned. That — not privilege escalation — is the exposure. Pin versions in catalog entries (lean-lsp-mcp==0.29.0) and keep free-form server entry behind an advanced door. Separately and non-negotiably: adding an MCP server must never be a tool the model can call. It is a human config action. Nothing in the current design permits it; keep it that way.
SSRF is a new surface. netguard.py guards inbound requests only. A user-authored HTTP tool means the adapter makes outbound calls to a user-supplied URL, internal addresses included. Curated packs are fine; a free-form URL field needs an allowlist or the same advanced-mode gate as free-form MCP servers.

The v2.5 failure mode is absence — and absence throws no exception

v2.4 gave every failure an owner, but its subject was things that break: an exception, a rejected key, a tool that raised. Every characteristic v2.5 failure is instead something that silently did not happen. The MCP server didn't start, so 23 tools aren't there. The role was created but the coordinator never learned it exists (gap 3), so it is never delegated to. The skill didn't resolve because the session is loose. The pack's key isn't set, so its tool 401s on first use. The user's proof still runs — it just runs without the thing they configured, and it looks exactly like a working system.
An except block cannot catch this. There is no exception at the moment that matters — the absence is the bug. So the v2.4 machinery has to be driven differently here: something must actively assert the positive and report when it does not hold. After starting a server, compare tools-registered against tools-expected. After building the spawn schema, check the role enum is non-empty when roles exist. After resolving skills, confirm the count matches what the project assigned. Each is one comparison, and each converts an invisible no-op into a degraded diagnostic with a remedy. This is the single most important thing in v2.5's error design, and it is why Phase G is not merely "add some codes."

One vocabulary, two moments. The same code must serve preflight ("you can't enable this yet") and run time ("this stopped working since you enabled it"). A user who saw "Lea can't find uvx" when enabling should see the same sentence if it later disappears — not a different phrasing of the same fact from a different code path.
Remedies must be actions where an action exists. The catalog comment already makes this argument — "a remedy that says 'check the key in Settings' is still work for the user to go and find; an action takes them there." Packs are the case with the most obvious buttons: ACTION_API_KEYS already exists and already focuses the right field; a pack needs the same for "open this pack's settings" and "re-run preflight."
Fail at save, not at run. A malformed role or pack should be rejected when the user presses Save, while they are still looking at the field that is wrong. parse_profile (profiles.py) already refuses unknown keys loudly for exactly this reason — a silently dropped tools: would hand a child the full toolset. Extend that discipline to every pack artifact, and the run-time codes above become rare rather than routine.

Naming: "capabilities" was invented jargon

An earlier draft of this work shipped a project tab and a picker called Capabilities — a word from the codebase's head, not the user's. Corrected on the user's call: a surface covering only skills says Skills; a surface covering both says Skills / MCP. Carried through the whole stack rather than just the label — components, types, API routes (/api/sessions/{id}/skills-mcp) and the table itself (session_skill_mcp_overrides, revision 0013), so the schema names the thing people actually read. Pre-existing uses of "capability" — the LSP handshake, and v2.4's degraded "reduced capability" copy — are untouched; they mean something else.

RETRACTED — AND THE REAL CAUSENo MCP tool was ever reachable from the UI

An earlier version of this box claimed the pack thesis had been confirmed — that scoping the skill made the agent use the MCP tools. That was wrong, and the evidence for it was misread. The "confirmation" was the model discussing lean_goal and lean_leansearch (it had read about them in the skill), not calling them.
Correction to my own evidence: I first "proved" this by finding zero MCP tool calls in timeline.data. That check was worthless — tool calls are not persisted at all (ToolCalled is streamed to the UI; the timeline stores only messages, code steps, edit notes, compactions and diagnostics), so that column is empty of tool calls for every tool. The conclusion survives on evidence that does hold: reading _with_subagents, and the tell in the model's own tool list — it named spawn_subagent and safe_verify, which build_toolset(None) never returns, so the run could only have been using an explicit allowlist.
The cause was a single line in _with_subagents: 
default_tools = [schema["name"] for schema in build_toolset(None)[0]]
return replace(cfg, tools=[*default_tools, "spawn_subagent", "safe_verify"], …)
It resolves the default toolset in the adapter, before the run starts, and passes the result as an explicit allowlist. MCP and HTTP tools register inside the run, into the per-activation overlay — so they were never in that snapshot, and an explicit list is a filter. Every UI run therefore shipped the seven built-ins and nothing else, while the MCP server started, warmed, pooled, and reported 23 tools correctly. Every layer was right and the tools were filtered out at the last one.
Fixed: LeaConfig.extra_tools lets a caller ask for "the default set PLUS these opt-ins" without naming the defaults — because naming them means snapshotting them. Resolution moves back inside the run, after everything has registered. A regression test asserts cfg.tools is None and that a tool registered mid-run still reaches the model.
Three lessons, and the third is the one that matters.
· A snapshot of a registry is not the registry. The old code even had a comment explaining that it resolved at call time "so this stays correct if the default set changes" — correct about which built-ins, blind to when.
· Never ask a model what tools it has. Two runs were spent on "do you have access to Loogle?" Its list was accurate and I dismissed it as hallucination, because a simulation I had written myself said otherwise. The model was right; my simulation used load_config() and never went through _with_subagents.
· Nothing here would have been caught by a test. Store resolved, bridge wired, registration worked, the pool warmed, 45/45 slices passed, and the feature did nothing. It took a human saying "it is still denying it" a third time — after I had twice explained the denial away.

Gap: a run keeps no record of which tools it used

Found while trying to verify the above. ToolCalled is streamed and rendered live, but never persisted — the timeline holds messages, code steps, edit notes, compactions and diagnostics only. For a system whose defining failure is a capability silently not being there, that means the one question you most want to ask afterwards — "did it actually use the thing I configured?" — is unanswerable from the record. It has to be watched live or not at all, which is exactly how a false "green" survived two rounds of testing here. Not fixed; recorded, because the cost only shows up in hindsight and the fix (a kind='tool' timeline row, or a per-run tool manifest) is a design decision, not a patch.

SPAWN-KILLERMCP tool names reached a child that had no MCP

Surfaced the moment delegation was first tried after the toolset fix: ToolError: unknown tool 'lean_build', and the spawn died.
A child is deliberately built with mcp_servers={} — each child would otherwise spawn another Lean server against the same 8.4 GB Mathlib (the A8 concern). So MCP tools live in the parent's registry and not the child's. But compose_child_tools validated declared names against the parent's live registry, so MCP names passed the check and then failed in the child's build_toolset — a hard failure at spawn, for a name that was entirely legitimate where it was checked.
It hit the generalist too, which is what made it total: a generalist's wanted-set IS the parent's whole live toolset, so every delegation broke — not just the four imported roles that name lean_goal explicitly. Fixed by composing against what the child will actually have (_child_available_names): the global registry plus inherited HTTP tools, MCP excluded. B4's soft-drop was already in place and did not help — it only fires for names unknown at composition time, and these were known there. The bug was the wrong reference set, not the wrong policy.

The overlap observation — now unexplained, and still open

Reinterpret with care: the run below had no MCP tools available at all (see the retraction above), so it says nothing about whether the agent prefers search_mathlib when both are offered. The overlap question is untested, not answered. It becomes testable for the first time now. First real run with MCP enabled ("Prove that the derivative of fun x : ℝ => x^2 is fun x => 2*x. Use the Lean LSP tools…"). The wiring worked: the server started, 23 tools registered, and the pooled process was still warm afterwards. The model did not use any of them. It reached for search_mathlib and suggest_imports — Lea's own built-ins — found deriv_pow_field, and compiled first try.
Not a wiring failure, a preference failure, and exactly what the plan warned about when lean-lsp-mcp was first measured: it adds tools that overlap what Lea already has (lean_leansearch vs search_mathlib). Given both, the agent picks the familiar one — and never inspects a goal with lean_goal, which is where the LSP tools actually beat the built-ins. Two contributing causes, both addressable:
· The skill was scoped to nothing, so its own instruction — "lean_goal — MOST IMPORTANT tool, use often!" — never reached the prompt. That is precisely the "when to use this" guidance C1 exists to carry, and it was inert.
· Nothing tells the model which to prefer. The system prompt says use search_mathlib for Mathlib lookups; nothing says when lean_goal is better. Two tools, no tiebreaker.
This is why "one-click MCP" was the wrong unit and a pack — server + recommended tool subset + a skill that teaches their use — was the right one. Resolved above: scoping the skill fixed it.

CAUGHT LATEA shipped route was unreachable, and the tests could not see it

GET /api/mcp-servers/defaults (A4's "Use my Lean project") never worked. FastAPI matches routes in declaration order, and /api/mcp-servers/{server_id} was declared first — so both static paths were swallowed and 404'd as "MCP server not found". A4 was marked Tested on the strength of unit tests that call the route functions directly and never exercise routing, so nothing could have caught it; it surfaced only when the same mistake repeated on D1 and that endpoint was hit over HTTP. The general lesson is narrow and worth keeping: calling a handler is not testing an endpoint.

THREE TIMES"Installed but scoped to nothing" is the failure this project keeps producing

It has now bitten three separate times in testing: the lean4 skill sat unscoped and silently never loaded (which produced the false "the model ignores MCP tools" conclusion); a broken server stayed scoped and fired on every run; and the Loogle tool was installed, left unscoped, and the run testing it could not have used it — the person testing had no way to tell.
The install-unscoped decision was mine and the reasoning still holds — a suggested item may duplicate something configured, and scoping should be deliberate. But the consequence was an absence with no signal. The badge did say "Unassigned": accurate, muted, and read as neutral metadata rather than as this does nothing.
Fixed at the Library layer, in the two shared components, so all three pages inherit it: the badge now reads "Not in use" in amber, and the scope control shows "Not in use yet — pick All projects or at least one project below, or Lea will never load this." This is G3's positive assertion applied one layer up: a run can assert that a configured capability contributed nothing, but only the Library can assert that a capability was never configured to contribute at all. Neither raises. Both have to be said out loud.

A regression I introduced, found by a test I nearly dismissed

Two ordering tests in test_bridge.py began failing intermittently under the full suite while passing in isolation — the shape of a flake, and I twice called it one. They are timing-sensitive (_wait_for with budgets), and my own change had added per-run startup work, so the honest move was to measure rather than re-run until green. Measured: materialize_roles() cost 22.46 ms per run — 50× every other resolution step — because it rewrote four role YAMLs into a fresh temp dir on every run, to produce files most runs never read (a run needs them only if the coordinator actually delegates). Fixed by caching the directory on a hash of the role rows, the same reasoning as A8's connection pool: the expensive part is not per-run state, so it should not have per-run lifetime. 22.46 ms → 0.50 ms, and the suite then passed three consecutive full runs.

Two findings that revise earlier advice

Dropping MCP for children is protection, not a bug. _child_config hardcodes mcp_servers={} (subagents.py:161,189). This was initially flagged as a defect — a premise-search scout with no search tools is backwards. But measurement reframes it: each child would spawn another Lean LSP against the same 8.4 GB Mathlib, on top of the one lsp_daemon.py already runs for lean_check. With DEFAULT_MAX_CONCURRENT_CHILDREN = 5, blanket-dropping is probably protecting laptops from swap. If it becomes per-role opt-in, gate it on concurrency — this is the one item here with a real resource cost and it needs a deliberate decision, not a flip.
Token bloat is not real — it was speculation, and the measurement disagrees. All 30 tools cost ~1,100 tokens of descriptions. The overlap concern stands, but it is behavioral (the model has two ways to search), not a context-size problem. The fix is "when not to use" in the descriptions, not trimming the toolset.

Patterns to copy

The skill lifecycle — author ∪ GitHub-import → DB row → scope → materialize per run → clean up in a finally. Packs should reuse this shape wholesale, including ghimport. · The scoped registry overlay (registry.py push_scope/pop_scope) — dynamic tools that exist only for the life of a run and cannot leak across concurrent activations. · Override-not-mutate (subagent_overrides.py) — user edits stored as a diff from the vendored default, so an untouched default keeps flowing through and "reset" is deleting a row. Exactly right for pack-shipped roles the user then tweaks. · load_overrides_checked — returns why it fell back, because a loader that silently returns {} makes failure undetectable by construction. Every pack loader must follow this.
